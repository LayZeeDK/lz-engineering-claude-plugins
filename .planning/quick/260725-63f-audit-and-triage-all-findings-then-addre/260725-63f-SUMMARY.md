### Why F4 was rejected -- what was deliberately NOT fixed

The finding predicted that the kata's `target: es5` with no `lib` makes a produced test using
`Array.prototype.includes`, `Object.entries`, `Object.values`, or `Array.from` emit new TS2550
errors the differential cannot absorb. Measured in a real differential run against the kata with
its toolchain linked in, one candidate method per run:

- **Every method the finding names produces ZERO new errors.** Root cause:
  `node_modules/@types/node/index.d.ts:28` carries `/// <reference lib="es2020" />`, and the kata
  tsconfig sets no `types`, so `@types/node` is auto-included and silently raises the program's lib
  to es2020 regardless of the es5 target. The predicted failure cannot occur.
- The real residual is three exotic methods -- `String.replaceAll` (es2021), `Object.hasOwn`
  (es2022), `Array.findLast` (es2023). For the latter two, `compile_error` is the CORRECT verdict:
  the kata resolves TypeScript **4.9.5**, which has no es2023 lib at all, so the produced test
  genuinely does not compile under the target's own pinned toolchain -- exactly what D-06 clause 1
  is for.
- **The proposed remedy is hazardous.** `--lib es2023` is rejected by TypeScript 4.9.5 with a single
  `TS6046` that appears in BOTH differential runs, so `newErrors` computes to 0 for every input,
  including a deliberately type-broken spec. Pinning a lib couples a target-agnostic gate to one
  compiler's accepted lib list and trades a zero-probability false positive for a real
  false-negative on the next target. The plan's own suggested `es2021` also closes only 1 of the 3.
- The secondary claim is refuted too: baseline is byte-identical with and without CLI `--strict`
  (21 errors, same code histogram, no TS7006), because tsconfig's explicit `noImplicitAny: false`
  takes precedence over the `strict` umbrella and the kata's own source contributes zero errors
  either way.

The one thing kept from F4 is the hazard its own remedy exposed -- see the deviation below.

## Deviations

**1. [Rule 2 - missing critical functionality] Fail closed on option/config-level tsc errors.**
This audit produced a vacuous differential twice from unrelated causes (F1's global-compiler config
abort; F4's invalid `--lib`). Both have the same shape: tsc fails before typechecking, emits an
identical error in both differential runs, and `newErrors` subtracts to 0 -- so the gate reports
"tsc clean" exactly when it could not check anything. A gate whose contract is to fail closed must
not have a silent path to a false clean. Added a four-line guard in `gradeRun` (TS5xxx/TS6xxx in
the baseline throws). Shipped in CM-2 as part of the F1 fix, same root cause.

**2. Deviated from the plan's recommended jest+test/jest runner pairing, with reason.** The plan
made jest the default and required a written reason to deviate. Two measurements justify it: both
kata runners emit the Jest-compatible shape `classify()` reads (so the "vitest 0.28 shape is
unstable" premise behind the hard-lock does not hold), and folder choice is NOT arm-independent as
the findings doc assumed -- the skill under test is Vitest-flavoured throughout its examples and
references, so a jest hard-lock would score the two skill arms `no_tests` for a folder choice the
skill itself encourages. That is an arm-BIASED artifact on the headline correctness number.
Path-keyed selection grades both of the kata's directories correctly and stops measuring folder
choice.

**3. Corrected the plan's stated rationale for `--coverage=false`.** The plan expected coverage text
interleaved on stdout that the brace-extraction fallback would have to fight. Measured: jest keeps
stdout pure JSON either way and adds a `coverageMap` field instead. The flag is still right, for
different reasons -- it keeps the gate from writing into the borrowed kata's `coverage/` directory
and it shrinks the payload. Recorded in `targets.json`.

**4. Touched `EVAL-RESULTS.md` beyond the plan's stated trigger.** The plan scoped it to an F3
WONTFIX caveat, which did not arise. Two spots became factually stale as a direct result of this
task's changes (the `selfcheck-red` one-liner, and a metered recipe that reproduced the
toolchain-less checkout), so both were corrected in CM-6.

**5. Installed the workspace's own pinned devDependencies.** This agent worktree had no
`.claude/skills/lz-red-workspace/node_modules` (gitignored, so not carried into a fresh worktree),
and the battery cannot run without it. Ran `npm ci` from the committed lockfile -- no new dependency,
no new package name, nothing added to `plugins/lz-tdd`. A junction to the main checkout's copy was
considered and rejected: a later `git worktree remove --force` could follow it and destroy the main
checkout's dependencies. Same data-loss reasoning as T-63f-01.
