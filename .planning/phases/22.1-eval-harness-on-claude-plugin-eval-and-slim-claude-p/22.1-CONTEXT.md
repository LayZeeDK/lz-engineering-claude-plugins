<decisions>
## Implementation Decisions

### Resumability (the gate before any paid run)
- **D-01:** Copy lz-gardener's resume model (`D:/projects/github/LayZeeDK/lz-gardener/tools/evals/eval-run.ts`,
  `slim-output.ts`); lz-oop's harness has no resume code (searched 2026-11-24), so lz-gardener is the closer fit Lars
  asked the research to pick. The rules carried over: a run whose result file exists is done and is never started
  again; `run` starts only runs without a result, so raising n adds runs and keeps the old ones; `resume <run dir>`
  continues a stopped slim session with `run-slim.ts --resume <session id>` into `result-resume-<n>.json` beside the
  first result; `rerun <run dir>` moves the old run into a `set-aside-<n>` folder and starts it fresh; a session ended
  by the usage limit exits 0, so its result text decides and the run counts as failed, not done; a run folder with
  outputs but no result is a run that died and is refused by `run` until rerun. -- **Reversibility:** costly -- every
  later round's run sets assume this layout.
- **D-02:** `claude plugin eval` has no resume or session option (`claude plugin eval --help`, 2.1.327), so its unit
  of resumption is one invocation per arm x model x case x run: `--case <name> --runs 1 --model <id> --output-dir
  <run set>/<arm>/<model>/<case>/run-<k>/ --json <same dir>/result.json --no-publish`. A finished `result.json` is a
  finished run; a stopped invocation loses at most its own run, which is "resume where its tool allows" for
  `plugin eval`. The harness aggregates the per-run results itself instead of relying on one invocation's report.
- **D-03:** "Shown working on a dry run" is two steps. First a free dry run: the run-set logic runs against a stub
  `claude` that writes canned results, is killed partway, and the next `run` starts only the unfinished runs (plus
  unit tests of the same logic). Then the first real pilot, which the pre-approval covers once step one passes: a
  small run set on both models, interrupted on purpose and resumed, which also records the per-run cost that the n
  recheck in ROADMAP 22.1 needs.
- **D-04:** A slim apply run that runs a test suite holds the machine's heavy-run lock the way lz-gardener does
  (`LZ_EVAL_HEAVY_LOCK`-style wrapper, `lars-shared-machine`); trigger and answer runs are light and do not.

### Where things run
- **D-05:** Trigger, answer and apply-without-shell cases run on `claude plugin eval`; cases that must run tests run
  on slim `claude -p` through `~/.claude/references/slim-claude-p/run-slim.ts` (Bash needs the OS sandbox, which
  native Windows lacks for `plugin eval`). Pre-decided in ROADMAP 22.1.
- **D-06:** A packaged variant is a `plugin eval` target, not a reason to switch to slim: each arm (the baseline
  copy, a later Phase 23 or 23.1 copy, a Phase 22 placement variant) is its own run set against its own packaged
  copy. The no-plugin baseline arm (`--ablation with-without`) runs once per model and case set, and further arms run
  with `--ablation none`, because the no-plugin arm is the same session whatever copy is under test. This amends the
  ROADMAP 22.1 parenthetical that listed packaged-variant A/B arms under slim (Claude's earlier wording, not a Lars
  ruling).
- **D-07:** Cases live at the repo root in `evals/lz-tdd/` (and `evals/lz-tdd-apply/` for the slim suites), outside
  the shipped plugin. A staging step packages the plugin with `git archive <ref>:plugins/lz-tdd` and copies the cases
  beside it into a git-ignored staging folder, because `plugin eval` reads cases only below a plugin root (lz-oop's
  `pre-eval` pattern). Packaging from a commit follows the 2026-11-07 ruling that evals use a packaged copy, never the
  source dir. Run outputs (local paths inside) stay git-ignored; a committed `RESULTS.md` per run set carries the
  numbers.
- **D-08:** The harness code lives in `tools/evals/` at the repo root with its own `package.json`, as erasable
  TypeScript with a `.test.ts` beside each script, type-checked, reviewed and security-reviewed (user-scope script
  bar, ROADMAP 22.1). Mutation testing uses the pinned lz-node-test StrykerJS runner (standing ruling, ROADMAP
  Backlog).

### Retirement
- **D-09:** Retire the eval runners only: the vendored skill-creator `run_eval` scripts, `run-*-chunks.mjs`,
  `grade-run.mjs`, `merge-judge.mjs`, `eval-status.mjs`, `extract-samples.mjs`, the e2e `run-e2e.mjs` drivers and their
  npm scripts, once each ported suite has reproduced (D-12). The deterministic check battery stays where it is in this
  phase (`npm run check` in each workspace, `routing-parse.mjs`, `check-rgr-routing.mjs`, `selfcheck-routing.mjs`,
  `build-variants.mjs`, `cycle-logs.ts`, the hygiene and package-link gates), because Phase 23 D-07 and D-08 edit those
  paths. Recorded result documents (`EVAL-RESULTS.md`, `RESULTS.md`, `*-RESULTS.md`) stay as historical records with
  their model labels unchanged. Amendment (Claude's call in the 2026-11-25 AFK run, not a Lars ruling; evidence in
  22.1-RESEARCH.md Open Questions 1-2, re-checked by the orchestrator): `e2e-nx/run-e2e.mjs`, `grade-routing.mjs`,
  `grade-red.mjs`, `arm-anchor.mjs` and `extract-samples.mjs` stay in this phase, because kept checks import or
  start them (`selfcheck-routing.mjs:53,55`, `selfcheck-red.mjs`) and `extract-samples.mjs` is the `typecheck`
  script of both workspaces; the first four retire after Phase 23 moves those checks. Retiring any `.mjs` deletes
  its `grandfathered-js.txt` line in the same commit.

### Models, runs and graders
- **D-10:** Every suite runs on `claude-opus-5-5` and `claude-sonnet-5-5` (`--model`), at Sonnet n=5 and Opus n=3,
  with the Opus n=5 rerun for a case that passes on Sonnet and fails on Opus; the model that ran is read from the
  CLI's own output (`system/init`, `modelUsage`, or the `plugin eval` JSON field that carries them), never from a
  harness field. Pre-decided in ROADMAP 22.1 (Lars 2026-11-24).
- **D-13:** Graders score the Phase 23 doing behaviour: `tool_used` Skill (the skill fired; must-not-fire as
  `min: 0, max: 0, arm: both`), `tool_used` Read with a path-tail `input_match` (the leaf was read), `tool_used`
  Edit/Write (the step made its change), and a `regex` on the final reply for the Phase 23 D-05 report line (`RED: ...
  -- fails: ...`, `GREEN: ... -- ... passes; <n> tests green`, `REFACTOR: ... -- tests green` or `REFACTOR: none --
  ...`). Slim suites grade the same facts from the transcript in TypeScript, plus a Bash call that ran the tests.
  Today's skills coach, so the baseline is expected to score low on these; that is the "before" the later phases
  measure against.
- **D-14:** Deterministic graders first; an `llm` grader only for substance a regex or tool check cannot see, judged
  with `--judge-model claude-sonnet-5-5` rather than the Haiku default, and scored as substance, not house vocabulary
  (finding recorded 2026-07-22: phrase-set graders measured vocabulary). Every grader gets a known-pass and a
  known-fail fixture, so a grader that cannot fail is caught before a paid run.
- **D-15:** Three arms where a skill is under test: no-plugin baseline and plugin-present with a natural short prompt
  (both from `--ablation with-without`), and an invoke arm as a separate case whose prompt starts with
  `/lz-tdd:<skill>`, so a trigger gap shows apart from content value (Lars's 2026-07-22 eval design requirement).
  Prompts stay short and written the way a developer types.
- **D-16:** Reports stay local (`--no-publish`).

### Baseline
- **D-17:** The baseline is a run set on a packaged copy of this phase's last commit (no skill text changes in 22.1),
  on both models, over every ported suite, after D-03 passes. It runs without a separate go-ahead under the
  2026-11-24 pre-approval. Its `RESULTS.md` names the commit, the models that ran (from CLI output), n, cost and wall
  clock.

### Suites to port (Lars ruling, 2026-11-24)
- **D-11:** Option B: port the live set, one suite per kind per skill, and keep the rest as records. Lars
  2026-11-24, verbatim: "D-11, which suites get ported: OK". -- **Reversibility:** costly -- it fixes which "before"
  numbers Phases 23 and 23.1 compare against. Background as put to Lars: the goal says "every lz-tdd eval suite", but
  several are no longer live: `d07-chunks/` and `heldout-d09.json` are splits and held-out sets of the trigger suites,
  `trigger-smoke.json` has 2 cases, `evl02-scenarios.json` and the three `evals.json` behaviour suites grade coach
  prose that Phase 23 removes, and `rules-ab-kata/` measured a user-scope rule rather than the plugin. Option A (port
  all ~20 literally): biggest phase, and the coach-prose graders would be ported only to be replaced. Option B
  (Claude's recommendation): port the live set as one suite per kind per skill -- one trigger suite per skill (today's
  trigger cases plus the held-out, reciprocal and chunk cases as tags), one doing-behaviour suite per skill rewritten
  from today's `evals.json` scenarios with D-13 graders, the `e2e-rgr-routing` corpus, and one slim apply suite per skill
  on a real repo already used (`e2e-red-srvx`, `e2e-nx` or `e2e-gilded-rose`, and a green-step target) -- and keep the
  rest as records. Option C: port only what Phases 22, 23 and 23.1 read (trigger, reciprocal, routing, one apply per
  skill). The suites kept as records are not ported and are retired with their runners (D-09); their result
  documents stay.
- **D-12:** "Reproduces one recorded result" means re-running one recorded cell of a ported suite
  on its recorded model and commit and landing inside the 95% Wilson interval of the recorded pass rate. It applies
  to suites whose grading carries over (trigger, reciprocal, routing, apply mechanical facts). A suite rewritten for
  doing behaviour has no recorded result, so it proves its graders on known-pass and known-fail fixtures (D-14)
  instead. If a recorded model is no longer served, the nearest served model runs and the record says so.
