## Implementation Decisions

### D1 -- Interleave arms by run index (auto-locked)

DEFECT: all six baseline runs executed 22:46-22:58, then treatment 23:00-23:10, then forcing
23:12-23:26. Arm is perfectly confounded with time-of-run.

FIX: **CORRECTED 2026-08-02 by research -- my original rationale here was wrong.** `run-e2e.mjs`
ALREADY interleaves by run index at `:1053-1059`, proved by the `r1` block in the same results tree.
What actually blocked interleaving for D-12 is that `--arm all` expands to the LEGACY trio
(`with_skill`/`no_skill`/`invoke_skill`), not the D-12 trio, so the orchestrator had to invoke once
per arm and thereby serialised them. The fix is a ~2-line `parseArgs` change giving the D-12 trio its
own expansion, NOT a 30-invocation shell loop.

Recording the wall clock IS a harness change after all: `meta.json` carries no start timestamp,
though `started` already exists at `:687` and only needs persisting. Add that one field so the
interleave is verifiable after the fact rather than asserted.

Whatever expansion token is added must NOT disturb `--arm all` itself -- crux 6 pins the nx
`--arm all` dry-run byte-for-byte.

### D2 -- Record the per-run pristine assertion (auto-locked)

DEFECT: all 18 runs shared one throwaway tree and no per-run pristine assertion appears in the
artifacts. The audit could not confirm isolation held.

FIX: the harness already resets between runs; what is missing is the RECORD. Capture, per run, the
evidence that the tree was pristine before the run started -- at minimum `git status --porcelain`
empty and HEAD at the pinned base -- and persist it alongside the run. Do NOT create a fresh
worktree per run; srvx is ~170 MB plus an install, and the reset is not the thing in doubt, the
absence of evidence is.

### D3 -- Cut the resolving antecedents (auto-locked)

DEFECT: the prompts are lexically ambiguous but referentially UNAMBIGUOUS. The forcing arm's own
audit said "settled" 6 of 6 and named the reason both times: `a1`'s "Stub **it**" resolves against
"there is no middleware for **it** here yet", and `a2`'s "Stub **that**" resolves against "Real
stdout is in the way". The manipulation check reported that the manipulation failed.

FIX: remove the resolving clause from each prompt so the contested word carries the ambiguity itself.
The forcing arm's audit text names the exact clause in each case -- use it. The prompt must stay a
short, natural developer request and must still name the pinned `test_dir`.

CONSTRAINT: after the edit, re-check that ground truth is still DETERMINATE. Removing an antecedent
can tip a prompt from "ambiguous with a right answer" into "genuinely underdetermined", which is
unmeasurable.

**RESOLVED 2026-08-02 by research -- the two prompts SPLIT, and this is now locked:**

- **`a1` gets a TARGETED cut.** Drop the absence assertion but KEEP the artifact noun (of the form
  "stub the middleware for it"). Cutting the whole clause collapses the referent onto "a correlation
  id" and destroys determinacy.
- **`a2` is EXEMPT -- do NOT cut it.** Its resolving clause is the only thing that introduces a
  collaborator at all. Remove it and "Stub that" points at `src/log.ts`, which is the WRONG answer,
  so the cut would not create ambiguity, it would invert the ground truth. `a2` also has no headroom
  to gain (see D6), so there is nothing to buy. Record the exemption and its reason in the target
  spec so a future reader does not "fix" it.

### D4 -- Guarantee delivery by INLINING into the treatment SKILL.md (auto-locked)

DEFECT: zero of six treatment runs opened the taxonomy. Verified by transcript grep with a passing
positive control. The treatment dose was zero, so the arm measured retrieval, not content.

FIX: inline the taxonomy content directly into the treatment tree's `SKILL.md` rather than shipping
it as a reference bullet.

WHY INLINE rather than pointing the forcing step at it -- the owner offered both. Inlining preserves
LEVER SEPARATION, which is the whole reason the round has three arms: arm 2 stays purely passive
content, arm 3 stays purely the active step. Pointing the forcing step at the reference would fuse
the two levers into one arm and make a positive result unattributable.

NOTE this changes the question arm 2 answers, and the write-up must say so: it is no longer "does the
reference get used and help", it is "does the content help WHEN GUARANTEED PRESENT". That is the
better question and it is the one D-12 actually asks.

### D5 -- Stop scoring a deliberate blunt red as failure (auto-locked, HIGHEST RISK)

DEFECT: `Error: correlationIdMiddleware is not implemented` matches NEITHER `ASSERTION_RE` NOR
`RUNTIME_RE`, so `rightReason` is false by FAIL-CLOSED DEFAULT and the run grades `wrong_reason`.
The grader's stated reason -- "a runtime/type error masquerading as an assertion failure" -- is
factually wrong; nothing detected a runtime error. Meanwhile `SKILL.md:89` calls a not-implemented
throw "a valid but blunter red". The gate failed the arm for obeying the skill under test.

FIX: recognise the deliberate blunt red as a valid RED.

THIS IS THE RISKIEST ITEM AND MUST NOT WEAKEN THE GATE. A deliberate blunt red is distinguishable
from an accidental runtime error by evidence already on hand: the throw originates in a file the
model's own diff ADDED or MODIFIED (it is in `changed_production_files`), and the message has a
not-implemented shape. An accidental `TypeError` from an unrelated path has neither property. Require
BOTH, keep `RUNTIME_RE` fail-closed for everything else, and prove the discrimination with a
canary in `grade-red --selfcheck` that a dead-end copy of the pre-change logic FAILS.

### D6 -- Raise k to 5 (auto-locked)

DEFECT: at k=3 a benefit is arithmetically unobservable against a 6/6 baseline, and harm needs a
67-point collapse to reach p<0.05.

FIX: k=5. That is 3 arms x 2 prompts x 5 = 30 runs. At ~$0.91/run measured, budget ~$27.

Rationale for 5 rather than higher: with D3 applied the ceiling should drop, which is what makes any
effect observable at all; k=5 gives 10 observations per arm and a 10/10 vs 6/10 split reaches
p ~ 0.04 one-sided. Going further buys little until we know the ceiling actually moved.

**PILOT GATE, added 2026-08-02 by research, and it is BLOCKING.** The prior round's discriminator was
correct on **18 of 18** runs -- non-empty on every `a1`, empty on every `a2`, in all three arms. That
is a CEILING, not a tie, and it falsifies the "42/44 corpus base rate leaves headroom" reasoning I
recorded earlier. k=5 buys observability ONLY IF the D3 cut actually moves that ceiling.

So before spending the ~$27 round: run a **baseline-only pilot, 3 runs on the rewritten `a1`, about
$2.70**, with a decision rule PRE-REGISTERED in the plan before the pilot runs. If the baseline still
resolves the rewritten prompt correctly every time, the ceiling did not move, the full round cannot
detect anything, and the honest action is to stop and report that rather than buy 30 runs of tie.

### D7 -- Re-key the TAXONOMY_TOKENS tripwire, do not delete it (auto-locked)

Surfaced by research while checking D4. `build-treatment.mjs` carries a tripwire keyed on
`!variant.artifactSrc`. Inlining removes that field, so the tripwire will fire loudly on the
treatment block the moment D4 lands.

It must be RE-KEYED ON LEVER IDENTITY (which arm this variant is), not deleted. Deleting it removes a
guard that exists to catch the taxonomy leaking into the wrong tree -- exactly the class of mistake
the N3 guard was hardened against elsewhere in this instrument.

Cleared with evidence in the same pass: inlining does NOT trip guard G17, whose walk root is
`repoRoot/plugins` only, and the generated trees live under `out/`, outside it.
