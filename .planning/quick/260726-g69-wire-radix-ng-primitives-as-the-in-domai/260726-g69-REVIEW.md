## Critical

### CR-01: `escapingLinks` never inspects the destination ROOT -- a linked toolchain source reopens T-63f-05 and reports clean

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:448-452` (walk starts *inside* the root),
`:1276-1300` (`copyToolchainPaths`), `:1538` (the only containment call)

**Issue:** `escapingLinks` seeds its stack with `path.resolve(root)` and immediately calls
`fs.readdirSync(dir)`. `readdirSync` FOLLOWS a directory link, so if `root` is itself a symlink or
junction the walk happily enumerates the far side and the root entry is never `lstat`ed. Meanwhile
`copyToolchainPaths` gates only on `fs.existsSync(src)`, which also follows links -- so a declared
toolchain path whose source is a link passes the fail-closed check, and `fs.cpSync(...,
{ verbatimSymlinks: true })` faithfully reproduces the link at the destination.

Verified empirically (read-only scratchpad probe against the real exported `escapingLinks`):

```
src exists: true
src is link: true
dest is link: true
dest link target: C:\...\Temp\rev-linkroot-...\outside-store
escapingLinks(dest, wt) -> []
```

The grading worktree's `node_modules` is a live junction into a tree outside the worktree, and the
guard whose entire job is "prove the copy is self-contained" reports zero escapes. The runner then
spawns model-authored code with that path live -- exactly the hole the per-grade copy exists to
close (T-63f-05), reached by a linked root instead of a link inside the tree.

**Failure scenario:** a future target declares `toolchain_paths` for a repo where `node_modules` (or
a package-level one) is a junction to a shared store -- a real pnpm/nx/Windows-disk-pressure layout.
The first grade runs the model's spec against a live path into that store; a spec that calls
`rmSync('node_modules/typescript', { recursive: true })` deletes from it. Crux 9 reproduces exactly
that spec shape every run and would not catch this variant. Not triggerable by GRC, SRVC, RXF or RXL
today (all three borrowed repos have real directories), so this is not a live incident -- but the
guard's own header commits to being target-independent, and `resolveToolchainPaths` just multiplied
the number of declared paths that have to hold the property.

**Fix:** fail closed on a linked source before copying anything -- one `if`, in the loop that already
pre-checks every source:

```js
for (const rel of relPaths) {
  const src = path.join(repo, rel);

  if (!fs.existsSync(src)) {
    throw new Error(/* unchanged */);
  }

  if (fs.lstatSync(src).isSymbolicLink()) {
    throw new Error(
      `grade-red: target '${id}' declares toolchain path '${rel}', but ${src} is a LINK rather than a ` +
        'directory. cpSync would reproduce the link, so the grading worktree would hold a live path ' +
        'outside itself and escapingLinks -- which walks INSIDE the root -- would not see it ' +
        '(fail closed, T-63f-05).',
    );
  }
}
```

Belt and braces: also have `escapingLinks` `lstat` its own root and push it onto `escapes` when it
is a link resolving outside `boundary`. Add the linked-root case to crux 9's
`checkMultiPathToolchainCopy` probe (a junction source is enough; the property under test is "the
destination is a reparse point", which junctions and symlinks share).

### IM-01: the widened boundary + single-hop resolution newly permits a two-hop escape that the register says is caught

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:439-443` (the claim), `:463-472` (single-hop
`path.resolve(dir, readlinkSync(p))`), `:1538` (walk set = `toolchainDests` only);
`RUN-GATE.md:575`; PLAN threat `T-g69-01`

**Issue:** before the change, `boundary === root`, so anything a link resolved *into* was by
construction also inside the walked tree and therefore transitively checked. After the change the
boundary (the whole worktree) is strictly larger than the walked set (the copied toolchain
destinations only), and resolution is a single lexical hop with no `realpath`. So:

- hop 1: `<armCwd>/node_modules/x -> ../<any repo directory>` resolves inside the worktree -> **now
  permitted** (it was flagged before);
- hop 2: `<armCwd>/<that repo directory>/y -> ../../../../..` is never examined, because that
  directory is checked-out repo content and is not in `toolchainDests`.

The guard header and `T-g69-01` both assert that "any `..` chain that leaves the worktree" still
fails closed. That is now false for a chain whose first hop lands in the un-walked part of the
worktree. This is the honest answer to "can you construct a link shape that is now permitted and
should not be" -- yes, and this is it.

**Reachability, checked:** requires the target's tracked content to carry an escaping symlink.
Verified `git ls-tree -r HEAD | rg '^120000'` = **0** in all three borrowed repos, so it is
unreachable in the current corpus, and everything inside the worktree is already reachable by the
executing spec through ordinary relative paths (T-g69-07 already accepts that). So the practical
exposure is nil; the defect is that a containment guard's documented guarantee overstates what the
code does, in a file whose whole discipline is "verify, do not assume".

**Fix:** cheapest is honesty -- amend the header paragraph and the `T-g69-01` mitigation to say
"any `..` chain whose FIRST hop leaves the worktree", and add one sentence naming the un-walked
region. If you would rather close it: resolve with `fs.realpathSync.native(path.resolve(dir,
readlinkSync(p)))` inside a try/catch (an unresolvable chain already reads as an escape), which
follows the chain and costs nothing on a tree with no chains.

### IM-02: the sibling copy site was not fixed -- `buildStandInRepo` still uses the defaulted `verbatimSymlinks`

**File:** `.claude/skills/lz-red-workspace/selfcheck-red.mjs:2122`

**Fix:** add `verbatimSymlinks: true` here too, with a one-line comment pointing at

### IM-03: the only unit-level check for the `verbatimSymlinks` bug silently SKIPs when the platform cannot write a relative link

**File:** `.claude/skills/lz-red-workspace/selfcheck-red.mjs:2548` (`if
(!isAbsolute(storeLinkText))`), `:2570-2576` (`if (copiedLinkResolvesInsideDest === false)`),
`:2627` (the SKIPPED parenthetical), `:2420-2432` (`linkDir`'s junction fallback)

**Issue:** `linkDir` falls back to an always-absolute Windows junction when `fs.symlinkSync(...,
'dir')` throws -- which it does on any Windows box without Developer Mode or elevation. When it
falls back, `storeLinkText` is absolute, `copiedLinkResolvesInsideDest` stays `null`, and the
assertion at :2570 is skipped because it only fires on `=== false`. The battery still prints OK and
exits 0; the only trace is a parenthetical appended to a success line: `[link relative-text
unavailable on this platform -- SKIPPED]`.

This file's own doctrine, stated twice in its header and twice in RUN-GATE, is that **a SKIP is not
a pass**. Every other SKIP in the battery is a top-level `console.log` naming what went unmeasured;
this one is a suffix on a message that says "OK".

**Failure scenario:** the containment fix is later "simplified away" on a machine where the probe
falls back (a CI runner, a second dev box, a fresh Windows install). The dedicated unit check
silently vanishes. The backstop -- `canary-rdxf-red`, which would throw with ~8,170 escapes -- itself
SKIPs when `primitives-pin` or its `node_modules` is absent, which is the normal state of any
machine other than this one. Both layers SKIP together and a reopened containment hole ships green.
On this machine it did work (confirmed: my run printed the message without the SKIPPED suffix), so
this is about every other machine.

**Fix:** when `linkDir` had to fall back, emit a real SKIP line in the same shape as the others --
`console.log('  [crux 9] SKIP -- this platform cannot write a relative directory link, so the
verbatimSymlinks discrimination went UNMEASURED; a SKIP is not a pass')` -- and add a row to
RUN-GATE Step 2's fixture table recording that this discrimination is platform-conditional.

### IM-04: `r1-focus-state.md` names the mechanism, not just the symptom -- cut one clause

**File:** `.claude/skills/lz-red-workspace/e2e-red-radix-ng/prompts/r1-focus-state.md:1`

You asked for a real judgement rather than a rubber stamp. Mine: **the clause "the same way they
style a focused control elsewhere in this library" is a pointer, not a symptom, and it should go.**
Three reasons, and I have tried to argue the other side below.

1. **It is not what a reporter observes; it is a diagnosis.** A consumer observes "my focus styling
   never applies to the calendar's focused day." The comparison to other controls presupposes the
   reporter already knows the library has a uniform focus-styling convention *and* that the calendar

2. **It names the gap in everything but the token.** `targets.json:30` states the gap as *"It is the

3. **It routes around the forbidden-token guard semantically.** `data-focus`, `data-focused` and

**The counter-argument, stated fairly:** RXF's declared axis is DISCIPLINE (coach-don't-drive), not

**What actually breaks:** not arm bias -- all three arms get the same bytes, so `with_skill` vs

**Fix (one line, zero measurement cost on the drive axis):**

### IM-05: `compile_error` on radix is unfalsifiable -- only a COUNT is recorded against a 55-error baseline

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:1729-1730` (`newErrors` computed and
discarded), `:1043` (`whyFor` reports the count), `:1808` (`new_tsc_errors` is the only field
written)

**Issue:** `tscResult.errors` holds the actual new diagnostic lines, but neither `whyFor` nor
`red-grade.json` records them -- only `new_tsc_errors: <count>`. On GRC and SRVC the baseline is
CLEAN, so "N new errors" is self-evidently the model's. On radix the baseline is **55 errors across
17 files**, and the differential is line-exact string subtraction (`withErrors.filter(l =>
!baseErrors.has(l))`). A produced spec that perturbs an existing diagnostic's text or position --
plausible for a spec that adds a module augmentation, a `declare`, or a type that changes inference
in a shared file -- produces "new" lines that are relocated baseline errors, not the model's.

**Failure scenario:** a real RXF/RXL run grades `compile_error`, `pass: false`, `why: "1 NEW tsc
--strict error(s) attributable to the produced test"`. The operator and the judge have no way to
check whether that error is the model's or a shifted baseline line, because the artifact records no
text. The verdict penalises the model and cannot be audited. This violates the file's own stated
doctrine -- `added_test_titles` / `attributed_failures` / `failure_excerpt` exist precisely "so an
operator can check the verdict rather than take it on trust", and `compile_error` on a dirty
baseline is now the one verdict with no evidence attached.

**Fix:** record the evidence, mirroring `failure_excerpt`:

```js
new_tsc_errors: tscResult.newErrors,
// The actual NEW diagnostics, capped. On a target with a DIRTY baseline (radix: 55 pre-existing
// errors) a count alone cannot be checked -- a relocated baseline line reads identically to a
// genuine new one.
new_tsc_error_lines: tscResult.errors.slice(0, 10),
```

Add a RUN-GATE residual line: on radix, read a `compile_error` cluster against the recorded lines
before treating it as a model failure.

### IM-06: the differential can still go vacuous -- `targetTscErrors` ignores spawn failure, and the dirty baseline makes a guard free

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:1324-1348`, consumed at `:1700` and
`:1728-1730`

**Issue:** `targetTscErrors` returns `text.split('\n').filter(l => /error TS\d+/.test(l))` and never
looks at `r.status`, `r.error` or `r.signal`. A tsc invocation that fails to produce output --
spawn failure, OOM kill, `maxBuffer` overflow, a crashed compiler -- yields an EMPTY array. On the
second (with-patch) run that means `newErrors` is `[]`, `classify` falls through clause 1, and the
produced test is reported **tsc clean**. `isConfigLevelTscError` only guards the BASELINE, and it
matches only `error TS\d+` lines, so it cannot see a run that produced none at all.

You asked specifically whether the differential is sound against a dirty baseline and whether it can
go vacuous. It is sound in the direction you were worried about (the 55-error baseline subtracts
correctly, and `canary-rdxf-compile` proves the project flag discriminates -- I watched it report 1
NEW error live). It can still go vacuous in this *other* direction, and the dirty baseline is what
makes the fix free: with 55 known baseline errors you now have a cheap invariant that a clean
baseline could never give you.

**Failure scenario:** a radix grade where tsc is OOM-killed on the second pass (a full Angular
project pass on a loaded machine during a 36-run fan-out is not exotic). `new_tsc_errors: 0`, the
runner then decides the verdict, and a type-broken produced test can grade `genuinely_red` /
`pass: true`. Silent. Exactly the failure mode T-63f-04 was written to eliminate, arrived by a
different route.

**Fix:** one guard at the differential, using the baseline you already have:

```js
const withErrors = targetTscErrors(armCwd, worktree, tscArgs);

// A second pass that produced FEWER lines than the baseline did not run to completion (OOM, spawn
// failure, maxBuffer). newErrors would subtract to 0 and report a type-broken spec as tsc clean.
if (baseErrors.size > 0 && withErrors.length < baseErrors.size) {
  throw new Error(
    `grade-red: the post-apply typecheck reported ${withErrors.length} diagnostics against a ` +
      `${baseErrors.size}-error baseline, so it did not run to completion and the differential ` +
      'cannot discriminate (fail closed, T-63f-04).',
  );
}
```

Cheaper still, and worth having regardless: return `{ lines, status }` from `targetTscErrors` and
throw when `status === null` (killed) or `r.error` is set.

### SG-02: `resolveToolchainPaths` accepts `.` and `.git`

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:1205-1247`

Probed against the real export:

```
"."      -> ["."]          "./" -> ["."]      ".//" -> ["."]
".git"   -> [".git"]       "packages" -> ["packages"]
```

`"."` makes the destination `armCwd` itself: `copyToolchainPaths` would copy the entire borrowed
repo (including its `.git` directory) over the worktree, and `removeToolchain` would then

will almost certainly die mid-copy on the `.git` file-vs-directory collision, but the function's own
comment promises "every other malformed entry throws before anything is created". Add
`if (normalised === '.' || normalised.split('/')[0] === '.git')` to the reject list.
