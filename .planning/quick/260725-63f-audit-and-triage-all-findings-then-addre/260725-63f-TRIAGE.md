## F1 -- CONFIRMED. The grading worktree has no toolchain.

### Source

`gradeRun` builds a detached worktree under `os.tmpdir()` (`grade-red.mjs:459`), runs the
differential typecheck (`:491`, `:499`) and the target runner (`:508`) inside it, and tears it down
in `finally` (`:535`). There is no install step anywhere in the file, and no hook between
`worktree add` and the first command, so an operator cannot insert one. Confirmed by reading.

### Reproduction

```
git --git-dir=<kata>/.git worktree add --detach <scratch>/f1-probe main
ls <scratch>/f1-probe/TypeScript/         -> app jest.config.ts package.json README.md test
                                             texttest_rig.py tsconfig.json vitest.config.ts
test -d <scratch>/f1-probe/TypeScript/node_modules   -> NO
```

`node_modules` is gitignored and untracked, so the fresh worktree has none. `targetTscBin` checks
`armCwd/node_modules/typescript/bin/tsc` then `worktree/node_modules/...`, finds neither, and
returns null. `targetTscErrors` then falls through to `npx tsc`.

### What the fall-through actually reaches -- worse than the finding states

```
cd <scratch>/f1-probe/TypeScript && npx --no-install tsc --version
  -> Version 6.0.3            (the GLOBAL tsc, not the kata's 4.9.5)

cd <scratch>/f1-probe/TypeScript && npx --no-install tsc --noEmit --strict
  -> tsconfig.json(4,15): error TS5107: Option 'target=ES5' is deprecated and will stop
     functioning in TypeScript 7.0. ...
  -> tsconfig.json(8,5): error TS5101: Option 'baseUrl' is deprecated ...
```

The compile ABORTS at config parse. It never typechecks a single source file. I then wrote a
deliberately type-broken spec into the probe worktree and re-ran:

```
  -> the SAME two TS5107 / TS5101 lines, nothing else
```

So the baseline error set and the with-test error set are identical, `newErrors` is 0, and
**D-06 clause 1 is silently disabled**: a produced test with blatant type errors grades as
tsc-clean. The finding predicted "the wrong compiler version"; the measured behaviour is
"no typechecking at all, reported as a clean differential". That is a false-negative on the
headline gate, not merely a fidelity issue.

The kata's REAL tsc is also unusable without the toolchain -- run by absolute path against the
same probe worktree it emits 33 errors, all of the `Cannot find name 'describe' / 'it' / 'expect'`
and `Cannot find module 'ts-jest' / 'chai'` kind. A produced test file would contribute the same
class of error under its own new path, which the differential CANNOT absorb, giving a false
`compile_error`. Both branches of the fall-through are broken; they just fail in opposite
directions.

### Fix and its offline check

After `worktree add` and before the baseline typecheck, create a Windows-safe directory junction
(`fs.symlinkSync(target, link, 'junction')`) from `armCwd/node_modules` to the target repo's real
`node_modules`. Fail closed with an operator-actionable error if the source is absent, instead of
falling through to the global resolver. Remove the link BEFORE `git worktree remove --force`, in
the same `finally`, so no recursive delete can follow it into the borrowed repo.

Verified the junction is safe to remove: `fs.rmSync(link, { recursive: true, force: true })` on a
junction reports `isSymbolicLink=true isDirectory=false` and unlinks the link only -- the kata's
`node_modules` entry count was 308 before and 308 after.

Verified the junction makes the gate work: with it in place, the kata's own tsc 4.9.5 produces a
21-error baseline (all inside `node_modules` .d.ts files, absorbed by the differential) and
correctly reports the deliberately-broken spec as NEW errors
(`test/vitest/probe-broken.spec.ts(2,7): error TS2322`, `(3,20): error TS2339`).

**Offline check:** the `canary-rundir` crux asserts `runner_version` is a real version rather than
the `unknown` sentinel. That value can only be read from a `node_modules` the worktree can see, so
it fails without the junction and passes with it.

### Additional guard folded into this fix (deviation, Rule 2)

This audit produced the vacuous differential twice from two unrelated causes (the global-tsc config
abort above, and an invalid `--lib` value under F4). Both have the same shape: tsc fails at the
option/config layer, emits an identical error in both differential runs, and `newErrors` computes
to 0 -- so the gate reports "tsc clean" precisely when it could not typecheck at all. A gate whose
stated contract is to fail closed must not have a silent path to a false clean. The F1 fix
therefore also asserts that the baseline typecheck contains no tsc option/config-level error
(`TS5xxx` / `TS6xxx`) and throws an operator-actionable error if it does. Four lines, same commit,
same root cause.

## F2 -- CONFIRMED. Prose-sniffed runner lock, and a miss that throws.

### Source

```js
const preferJest = /jest/i.test(runnerSpec.runner_preference || '') && runnerSpec.jest;
const runnerName = preferJest ? 'jest' : runnerSpec.vitest ? 'vitest' : runnerSpec.jest ? 'jest' : null;
```

Evaluated against the real `targets.json` rather than eyeballed:

```
runner_preference mentions "jest": true
preferJest truthy:                 true
selected runnerName:               jest
targets.json test_dir:             test/vitest/
selected runner command:           npx jest <producedTestFile> --json
```

`runner_preference` is a prose sentence. Any prose that mentions the runner's name makes the
selector truthy, so the field cannot express "prefer vitest" at all. The selected runner and the
configured `test_dir` disagree by construction.

### Reproduction (kata `TypeScript/`, read-only, `--coverage=false`)

```
npx jest test/vitest/gilded-rose.spec.ts --json --coverage=false
  -> exit 1, stdout 0 bytes
  -> stderr: "No tests found, exiting with code 1"
             "roots: ...\app, ...\test\jest - 3 matches"
             "Pattern: test\vitest\gilded-rose.spec.ts - 0 matches"
```

Positive control inside the collected root:

```
npx jest test/jest/gilded-rose.spec.ts --json --coverage=false
  -> exit 1, stdout 4455 bytes of valid JSON, no coverageMap, first byte '{'
  -> numTotalTests=1 numFailedTests=1, testResults[0].assertionResults[0].status='failed'
```

`gradeRun` feeds only `runRes.stdout` to `parseRunnerJson` (`:515`), so the 0-byte case throws
"runner produced empty output" and no `red-grade.json` is written. Confirmed by source.

### Two corrections to the finding

**(1) The vitest JSON shape is NOT unstable -- measured.** The finding, `targets.json`, and
RUN-GATE Step 2 all rest on "vitest 0.28's JSON reporter predates the 1.x shape, so a genuine
difference would surface only at the metered run". Measured against the kata's actual vitest 0.28:

```
npx vitest run test/vitest/gilded-rose.spec.ts --reporter=json
  -> stdout 1016 bytes, first byte '{'
  -> numTotalTests=1 numFailedTests=1
  -> testResults[0].assertionResults[0].status='failed'
  -> failureMessages[0]="expected 'foo' to be 'fixme' // Object.is equality"
```

That is the Jest-compatible shape `classify()` reads, and the message matches `ASSERTION_RE` and
not `RUNTIME_RE`, so it classifies `genuinely_red` correctly. Both runners are usable. The premise
that justified hard-locking to jest does not hold for this target.

**(2) Directory choice is NOT arm-independent.** The finding calls the folder lottery
"uncontrolled and arm-independent". It is not. The skill under test is Vitest-flavoured throughout:
`plugins/lz-tdd/skills/lz-red/SKILL.md` and five of its references show
`import { describe, it, expect } from 'vitest'`, and it ships a whole
`references/vitest-typescript-mechanics.md`. The `with_skill` and `invoke_skill` arms are therefore
nudged toward vitest idiom while `no_skill` is not. A gate hard-locked to jest plus jest-only
collection roots would systematically score the two skill arms `no_tests` for a folder choice the
skill itself encourages -- an arm-BIASED grader artifact on the headline correctness number, which
is exactly the class of defect the project's own `unbiased-review-beats-primed` lesson exists to
catch.

### Fix and its offline checks

(a) **Machine-readable selector, keyed by path.** Replace prose sniffing with an explicit
`runner_select` map in `targets.json` from repo-subdir-relative test-path prefix to runner name,
plus a `runner_default`. `grade-red` selects the runner whose collection root contains the produced
test, falling back to the default. Fail closed if the selected name has no command. This deviates
from the plan's "jest paired with the jest-collected dir" default; the written reason is correction
(2) above plus correction (1), which removes the only argument against vitest. Both of the kata's
supported dirs now grade correctly, so the gate stops measuring folder choice.

(b) **Coherent `test_dir`.** `test_dir` / `test_dir_note` are rewritten to describe the selector and
name the default rather than pointing at a directory the selected runner cannot see. The runner
command also gains `--coverage=false`. Note a further correction: the plan's stated reason for that
flag -- coverage text interleaving on stdout, which `parseRunnerJson`'s brace-extraction fallback
would have to fight -- is not what happens. Jest keeps stdout pure JSON either way and adds a
`coverageMap` to the payload instead. The real reasons the flag is right are that it keeps the gate
from writing into the borrowed repo's `coverage/` directory and that it shrinks the payload.

(c) **stderr into the no-tests disambiguation.** When stdout will not parse, check both streams
against the existing `NO_TESTS_RE`. On a RECOGNIZED signal, synthesize the minimal runner report
that drives `classify()` to `no_tests`, carrying the observed message so the excerpt stays honest.
Anything else still throws. Both runners' misses are covered by the existing pattern, measured:
jest emits "No tests found, exiting with code 1" and vitest emits "No test files found, exiting
with code 1".

**Offline checks:** `canary-rundir` grades a fabricated runDir end to end and asserts the recorded
runner is the selected one -- it cannot pass while the gate throws on a collection miss or picks a
runner that cannot see the test. `canary-nocollect` places the produced spec outside every
collection root and asserts the verdict is `no_tests` with `pass:false` and specifically that the
call did not throw; reverting (c) alone makes exactly that assertion fail.

### Residual, documented not fixed

A vitest-idiom spec written into `test/jest/` still selects jest, is collected, and fails at import
-- a `collection_error`. Path-keyed selection removes the folder half of the bias; the import-idiom
half cannot be removed without overriding each runner's collection roots, which is more mechanism
than the risk warrants. Recorded as a named limitation in RUN-GATE.md under CM-6 so the operator
reads any `collection_error` cluster as a possible instrument artifact rather than a skill result.

## F3 -- CONFIRMED as a prompt fix.

### The premise is factually false

The prompt opens: "The tests for `app/gilded-rose.ts` are all green right now." Both shipped
placeholder specs assert `expect(items[0].name).toBe('fixme')` against an item constructed as
`new Item('foo', 0, 0)`, and `updateQuality()` never renames items. Measured, both runners:

```
jest   test/jest/gilded-rose.spec.ts   -> numFailedTests=1
          "Expected: \"fixme\"  Received: \"foo\""
vitest test/vitest/gilded-rose.spec.ts -> numFailedTests=1
          "expected 'foo' to be 'fixme' // Object.is equality"
```

### The judgment call

Against the fix: the false premise is byte-identical across all three arms, so it is symmetric
noise rather than arm bias, and the prompt was subagent-reviewed in 21-01 for non-leading phrasing.

For the fix, and decisive:

1. The corruption it invites is one-directional on the gate that produces the headline. A model
   told everything is green may repair the placeholder. If it repairs and adds nothing, every
   assertion passes on a test-only diff and the run grades `false_green` -- a correctness failure
   manufactured by the instrument.
2. The 21-01 property at risk is "non-leading", and the fix is a DELETION. Removing a claim cannot
   make a prompt more leading; the result is shorter and more neutral.
3. Byte-identity across arms is structural, not incidental -- all three arms read the same file, so
   crux 2's parity assertion is unaffected. Re-asserted rather than assumed after the edit.
4. It is free. No `results/` tree exists, so no captured run depends on the current wording.

Verdict: fix the prompt. Replacement, preserving the original's verb phrasing and naming the target
only by path:

```
What's the next failing test you'd write for `app/gilded-rose.ts`? Go ahead and add it.
```

Short, human, non-leading, names no behavior gap and no smell, and makes no claim about the current
pass/fail state of the existing tests.

**Offline check:** crux 2 gains an assertion that the prompt body contains none of a small set of
test-state-claim tokens defined in the checker. Reverting the prompt makes that assertion fail. The
token set is chosen so the replacement text does not trip it -- "failing test" is the ask, not a
claim about existing tests.

## F4 -- REJECTED. The stated mechanism does not exist in the gate path.

The finding predicts that the differential typecheck runs under the kata's `target: es5` with no
`lib`, so a produced test using `Array.prototype.includes`, `Object.entries`, `Object.values`, or
`Array.from` yields new TS2550 errors the differential cannot absorb, producing a false
`compile_error`.

### The isolated mechanism is real

A bare probe file, compiled by the kata's own tsc with the kata's target and no project context:

```
tsc --noEmit --strict --target es5 f4-probe.ts
  -> TS2550 Property 'includes' does not exist on type 'string[]'
  -> TS2550 Property 'entries' does not exist on type 'ObjectConstructor'
  -> TS2550 Property 'from' does not exist on type 'ArrayConstructor'
```

### But it does not fire in the gate path -- measured

The gate does not compile a bare file. It runs a whole-project differential in `armCwd` with the
kata's `tsconfig.json`, which sets no `types`, so every installed `@types` package is auto-included.
Running the real differential in a junctioned worktree, one candidate method per run, comparing the
with-test error set against the baseline:

| tsc args | new-error cases |
|----------|-----------------|
| current, no `--lib` | `String.replaceAll` (es2021), `Object.hasOwn` (es2022), `Array.findLast` (es2023) |
| `--lib es2021,dom` | `Object.hasOwn`, `Array.findLast` |
| `--lib es2022,dom` | `Array.findLast` |
| `--lib esnext,dom` | `Array.findLast` |

`includes`, `Object.entries`, `flat` and `Array.at` produce **zero** new errors in every
configuration, including the unmodified current one. Root cause:

```
node_modules/@types/node/index.d.ts:28:  /// <reference lib="es2020" />
```

`@types/node` is auto-included and its triple-slash directive raises the program's lib to es2020
regardless of the `es5` target. Every method the finding names is at or below es2020. The predicted
failure cannot occur.

### The proposed remedy is worse than the residual

What survives is three exotic methods. Two of those are not fixable at all on this target: the kata
resolves TypeScript **4.9.5**, whose maximum ES lib is `es2022`, so `Array.findLast` has no
typings to pin and `Object.hasOwn` needs the very top of the accepted range. For a produced test
that uses them, `compile_error` is the CORRECT verdict -- the test genuinely does not compile under
the target repo's own pinned toolchain, which is precisely what D-06 clause 1 is for.

And the remedy carries a measured hazard. `es2023` -- one step past what the finding suggests
scaling to, and the value a reader would reach for next -- is rejected by TypeScript 4.9.5:

```
error TS6046: Argument for '--lib' option must be: 'es5', 'es6', ... 'es2021', 'es2022', 'esnext', ...
```

That single TS6046 line appears in the baseline run AND the with-test run, so `newErrors` computes
to 0 for every input, including a deliberately type-broken spec. Pinning a lib hardcodes a
TypeScript-version-dependent value into a gate that is meant to be target-agnostic; on the next
target with an older or newer compiler it silently disables D-06 clause 1 instead of erroring. That
trades a zero-probability false positive for a real false-negative.

### The secondary claim is also refuted

The finding says CLI `--strict` re-enables `noImplicitAny`, which the kata tsconfig sets to `false`,
inflating the baseline. Measured, same worktree, same junction:

```
--noEmit --strict   -> 21 errors {TS2691:5, TS2403:7, TS1383:8, TS2420:1}
--noEmit            -> 21 errors {TS2691:5, TS2403:7, TS1383:8, TS2420:1}
```

Byte-identical. No TS7006 appears in either. TypeScript gives an explicitly-set individual
strictness flag precedence over the `strict` umbrella whatever its source, so tsconfig's
`noImplicitAny: false` wins, and the kata's own source contributes zero errors either way -- all 21
baseline errors live in `node_modules` .d.ts files. There is no baseline inflation to comment on.

### Disposition

No fix, no `canary-modernlib` fixture, no CM-4. Task 3 is skipped. The one thing worth keeping from
this finding is the vacuous-differential hazard its own remedy exposed, which is folded into the F1
fix as a fail-closed guard on option/config-level tsc errors.

## F5 -- CONFIRMED, including the Step 3a knock-on.

### What Step 2 currently requires and costs

Step 2 frames the residual risk as "runner-JSON shape drift" and offers two options: a preferred
canary costing ONE real metered run captured and then graded, or an offline alternative that adds a
`jest` devDependency to the workspace so the fixtures can exercise the jest `--json` shape.

### Both options are obsolete

The shape risk Step 2 exists to de-risk was closed during this triage, offline and at zero spend.
Both of the kata's runners were run against the real kata and both emit the Jest-compatible shape
`classify()` reads (jest 29: 4455 bytes, `numFailedTests=1`; vitest 0.28: 1016 bytes,
`assertionResults[0].status='failed'`, `"expected 'foo' to be 'fixme'"`). Step 2's premise that a
shape difference "would surface ONLY at the metered run" is refuted.

The offline alternative is moot on top of that: it proposes installing jest into the workspace, but
the kata already has jest 29 installed, and the fabricated-runDir canary uses the target's own
toolchain rather than the workspace's. No dependency is needed.

### A fabricated runDir is strictly cheaper and strictly broader

From `gradeRun`'s source, a runDir contributes exactly two files -- `diff.patch` (`:407`) and
`meta.json` (`:417`, requiring a `changed_files` array). Everything else comes from `suite.json` and
`targets.json`. So a canary needs no capture and no spend. It exercises the worktree build, the
junction, the differential typecheck, runner selection, the runner invocation, `classify()`, and
`red-grade.json` -- and it catches F1 and F2, neither of which a shape-only check can see. It still
needs the kata on disk, so it inherits crux 3's SKIP-if-absent discipline.

Paths in both files must be ROOT-relative. Verified from `run-e2e.mjs:613`: `changed_files` comes
from `git diff --cached --name-only`, which prints repo-root-relative paths, and `diff.patch` comes
from `git diff --cached`, applied by `gradeRun` at the worktree root. `gradeRun` strips the
repo-subdir prefix itself when handing the path to the runner (`:506`).

### The Step 3a knock-on (folded in, not raised separately)

RUN-GATE Step 3a tells the operator to create the apply checkout with
`git worktree add -b red-run-<stamp>`. That is the same mechanism proven toolchain-less under F1, so
the model under test cannot run the test it writes. The "fail for the right reason" verification
behaviour is suppressed in all three arms at once. Same root cause as F1, same fix shape, and it is
an operator instruction rather than code -- so it belongs in the RUN-GATE rewrite. Handled inside
CM-6 as an explicit install-or-link step for the apply checkout, positioned before the drive
command, with the reason stated rather than just the command. Not raised as a separate finding:
`commit_boundaries` defines CM-1..CM-6 keyed to F1..F5, so a standalone item would have no commit
path.

### Fix and its offline check

Rewrite Step 2 so the zero-spend canary is the REQUIRED pre-fan-out gate, naming the exact offline
command and what it proves; demote the metered single-run canary to an optional extra; delete the
obsolete offline-alternative bullet and say plainly that it is moot; and correct the narrow "the
only remaining hazard is reporter-shape drift" framing.

Doc-only findings have no revert-and-reassert mechanism, so per the plan this section carries a
positive `rg` content assertion over the rewritten section instead, run also against the pre-edit
file from git to show it discriminates. Recorded in the CM-6 commit body.
