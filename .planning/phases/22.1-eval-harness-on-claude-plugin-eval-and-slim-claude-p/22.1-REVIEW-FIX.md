## Fixed Issues

### CR-01: Slim graders and scaffold scripts are read from the working tree at run time, after the uncommitted-cases check

**Files modified:** `tools/evals/eval.ts`, `tools/evals/slim.ts`, `tools/evals/slim.test.ts`
**Commit:** 5022325
**Applied fix:** eval.ts reads each slim case's graders and scaffold script bytes once, right after the
uncommitted-cases check and before staging, into a `cases` map in the slim context (`readCaseInputs`).
`settleSlim` now takes the graders to grade with, so a resumed or finished run is graded with the snapshot,
and `runScaffold` takes the script bytes and runs them from `raw/scaffold.sh` (which also keeps the script a
run started with beside its output). The snapshot replaces the pre-spawn grader read that was thrown away.

### WR-01: A tool_used grader counts failed and denied calls as if they happened

**Status:** fixed: requires human verification (it changes what a slim `tool_used` grader counts)
**Files modified:** `tools/evals/grade.ts`, `tools/evals/trace.ts`, `tools/evals/check-cases.ts`, `tools/evals/grade.test.ts`, `tools/evals/trace.test.ts`
**Commit:** 6667dbf
**Applied fix:** limited to slim runs. `runEvidence` (slim only) now keeps a call only when it took effect: not
refused, and either not an error result or a command that ran and exited non-zero. `ToolCall` gains `exitCode`,
read from an error result that starts `Exit code <n>`. `traceEvidence` (plugin-eval and crosscheck) is unchanged,
so the model still counts what the CLI counts; no CLI documentation or saved trace shows the CLI leaving out failed
or refused calls, so plugin-eval grading was not touched.

The reviewer's suggested `!call.denied && !call.isError` was not applied as written. Measured in the baseline-22.1
slim transcripts (`~/.claude/projects/D--tmp-slim-claude-p-runs-baseline-22-1-*`): a Bash call whose test run exits 1
is an error result that starts `Exit code 1` (36 such results with the gilded-rose prefix alone), so excluding every
error would fail `ran-tests` on exactly the red step it checks. The same transcripts also show refusal texts that
`denied` does not match ("This command requires approval", 31; "This Bash command contains multiple operations. The
following part requires approval", 20; "A variable ... can't be checked before it runs"), so the rule keys on the
`Exit code` prefix rather than on the refusal text.

Lars should know: the baseline-22.1 slim verdicts were graded with the old count. A rerun or resume of a few of its
slim runs would put new-count verdicts beside old ones in one arm, and `aggregate` does not tell them apart (the
`casesTree` check does not cover grading rules). Compare a later slim run set with baseline-22.1 on `tool_used`
graders only after checking whether any of its runs had refused or failed matching calls.

### WR-02: The shared stage folder's lz-tdd/ is rebuilt in place whenever HEAD's case trees change

**Files modified:** `tools/evals/stage.ts`, `tools/evals/eval.ts`, `tools/evals/plugin-eval.ts`, `tools/evals/grade.ts`, `tools/evals/stage.test.ts`, `tools/evals/eval.test.ts`, `tools/evals/plugin-eval.test.ts`, `tools/evals/grade.test.ts`
**Commit:** 4a496c8
**Applied fix:** each committed cases tree gets its own case target, `<stage root>/<sha12>/lz-tdd-<first 12 hex of
sha256(casesTree)>`, built once (into `<target>.tmp-<pid>`, then renamed; a copy another process renamed into place
first wins) and never deleted. `stageRef` returns the staged facts with the target instead of writing `stage.json`;
the plugin-eval target is the case target of the cases tree the run records (`pluginEvalTarget(stageRoot, run,
casesTree)`); `crosscheck` reads graders from the case target of the result's own `casesTree` and leaves the run
unchecked ("no stage holds the cases tree ...") when no such folder exists.

Behaviour changes Lars should know:
- `eval.ts stage <ref>` now prints the case target path (`.../<sha12>/lz-tdd-<key>`) instead of `.../<sha12>`. The
  command line itself is unchanged.
- There is no fallback to the old `<sha12>/lz-tdd` layout. Re-running `crosscheck` on baseline-22.1 now reports its
  plugin-eval runs as unchecked unless a stage of their commit exists for the cases tree their result.json records,
  which needs a checkout whose HEAD has that cases tree. The old `lz-tdd/` folders and `stage.json` files under
  `dist/eval` are left in place and no longer read.
- Old case targets accumulate under `dist/eval/<sha12>/` (one per cases tree staged); nothing prunes them.

### WR-03: The pre-spawn grader read does not compile regexes, so a bad pattern fails only after the session is paid for

**Files modified:** `tools/evals/grade.ts`, `tools/evals/grade.test.ts`
**Commit:** 85be4f2
**Applied fix:** `readGrader` compiles `pattern` with its `flags` and `input_match`, and refuses `min` above `max`,
each with an error naming the grader file. Since CR-01, eval.ts reads every slim case's graders before the first
spawn, so a bad grader now stops `run`, `rerun` and `resume` before anything is paid for. The committed graders all
still read (`check-cases: OK - 19 suites, 169 cases, 101 grader definitions, 101 fixtures`).

### WR-04: A run-set selection naming an unknown case or tag silently plans nothing

**Files modified:** `tools/evals/run-set.ts`, `tools/evals/run-set.test.ts`
**Commit:** 3b9cecb
**Applied fix:** `planRuns` throws when a selection's `cases` names a case the suite does not have, and when a
selection (by tags, names or both) matches no case. The committed run sets were planned with the new code from a
scratch script: baseline-22.1 456 runs, pilot-22.1 58, repro-22.1 93 (counts not compared with a run of the old
code). `tpp-turns-22.1` fails to plan because its suite `trigger-lz-tpp-turns10` has no folder under evals/; that
error comes from `findSuite`, which runs before the new checks, so this fix does not cause it.

### WR-05: The default lock booking can exceed heavy-lock's 1440-minute cap, and rerun has already moved the runs aside when it fails

**Files modified:** `tools/evals/eval.ts`, `tools/evals/run-set.ts`, `tools/evals/run-set.test.ts`
**Commit:** 43e5a83
**Applied fix:** `defaultLockMinutes(runs, concurrency)` in run-set.ts books each run's timeout plus 2 minutes, with
the plugin-eval part divided by `--concurrency` (rounded up) and the slim part summed, since slim runs go one at a
time. When the runs need the lock, `run`, `rerun` and `resume` refuse a booking above 1440 minutes in the pre-spawn
checks, with a message naming `--lock-minutes` and splitting the runs into parts. `rerun` now calls `setAside` inside
the `withHeavyLock` callback (through a `prepare` callback of `startRuns`), so a refused acquire leaves the run set
untouched. The command line is unchanged.

### WR-06: The `claude plugin eval` child has no timeout, so a hung CLI holds the timing slot forever

**Files modified:** `tools/evals/run-set.ts`, `tools/evals/plugin-eval.ts`, `tools/evals/slim.ts`, `tools/evals/run-set.test.ts`
**Commit:** f1b0d49
**Applied fix:** `spawnLogged` takes an optional timeout and returns `{ status, timedOut }`. When the timeout fires it
stops the child and every process the child started: `taskkill /PID <pid> /T /F` on Windows, and off Windows a
kill of the child's own process group (the child is started detached only when a timeout is set).
`startPluginEvalRun` gives each CLI invocation twice its suite's `timeoutMinutes`, since one invocation runs the with
arm, the without arm and the judge. The default is 2 x 15 = 30 minutes, about 12 times the longest plugin-eval run
in baseline-22.1 (152 s, read from its result.json files); a suite overrides it through `timeoutMinutes` in its
suite.json. A timed-out run is settled as `failed` with `raw/refused.txt` reading `timed out after <n> min`, so it
is never counted as done and shows as a died run for `rerun`. Slim runs keep run-slim's own `--timeout-min` and get
no second timer.

Not verified: the off-Windows process-group kill (this machine runs Windows only), and whether a real
`claude plugin eval` stopped this way leaves its `--keep-temp` sandbox behind (the traces are not copied on a
timeout). The lock booking (WR-05) still books `timeoutMinutes + 2` per run, so a run set whose runs hang can still
hold its slot past the booked end, now by a bounded amount.

### WR-07: The with/without table pools every arm that has a plugin into one with side

**Files modified:** `tools/evals/aggregate.ts`, `tools/evals/aggregate.test.ts`
**Commit:** bc00c9e
**Applied fix:** the table now pools per suite and plugin arm, never across arms:
- the with side of a row is the runs of one arm that has a ref, for one suite, model and grader;
- the without side is, for a with-without suite, the CLI's without verdicts of that same arm's runs; for any other
  suite, the runs of every cell without a ref (all ref-less arms together, as before); for an invoke twin, its
  natural suite's without side taken the same way for that arm;
- each verdict (`discriminates`, `does not discriminate`, `no without arm`) is per suite and plugin arm, and a suite
  run only by ref-less arms gets no verdict, since it has no with side.

RESULTS.md gains an Arm column in both the verdict table and the row table. The committed
`evals/results/baseline-22.1/RESULTS.md` still has the old layout; it was not regenerated, because `aggregate`
overwrites its hand-written Notes. Its numbers should not change, since its two plugin arms (`head`, `srvx`) run
disjoint suites (inferred from the review; not checked by regenerating it).
