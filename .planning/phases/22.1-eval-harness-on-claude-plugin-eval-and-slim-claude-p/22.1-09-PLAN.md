## How ran-tests is graded (read in tools/evals/grade.ts)

- A slim `tool_used` grader counts the calls whose tool name is listed and whose input matches: `passes` tests
  `input_match` against `JSON.stringify(call.input)`, so the text it sees is the whole input object, for a Bash call
  `{"command":"...","description":"..."}` with quotes inside the command as `\"` and newlines as `\n`.
- `runEvidence` keeps only calls that took effect (not refused; a command that ran and exited non-zero counts).
- The committed pattern is `vitest|jest|npm (run )?test`, in the eight `ran-tests.md` files and in the fixture. It
  matches the runner's name anywhere in that text: in a path, in a quoted string, in the description.
- The fixture has one pass evidence and one fail evidence; the fail evidence may hold several calls (min is 1, so
  it fails only when none of them matches). check-cases allows one fixture per grader definition and reports a
  definition without a fixture, so the grader fields of the fixture must equal the definition in the eight files.
  The twin rule requires the natural case and its invoke twin to hold the same graders.

## The new pattern (measured in planning, 2026-11-28 at 73ec9d4)

73ec9d4 differs from 5399451, the commit the gate baselines of this plan cite, in `.planning/` files only
(`git diff --stat 5399451..73ec9d4 -- tools/evals evals` prints nothing, measured), so those baselines hold at both.

The `input_match` value for the eight files, verbatim, in single quotes (it holds no single quote; 149 characters):

```
"command":"(?:(?:[^"\\]|\\.)*?(?:&&|\|\||[;|(]|\\n))?\s*(?:\w+=(?:[^\s"\\]|\\.)*\s+)*(?:npx\s+(?:vitest|jest)\b|npm\s+(?:test|run\s+(?:test|vitest)))
```

The same string as the JSON value of `inputMatch` in the fixture (every backslash doubled, every double quote
escaped):

```
"\"command\":\"(?:(?:[^\"\\\\]|\\\\.)*?(?:&&|\\|\\||[;|(]|\\\\n))?\\s*(?:\\w+=(?:[^\\s\"\\\\]|\\\\.)*\\s+)*(?:npx\\s+(?:vitest|jest)\\b|npm\\s+(?:test|run\\s+(?:test|vitest)))"
```

What it says: inside the `command` value, at its start or after `&&`, `||`, `;`, `|`, `(` or a newline, behind any
number of `NAME=value` prefixes, stands `npx vitest`, `npx jest`, `npm test`, or `npm run` with a script whose name
starts with `test` or `vitest`. Neither the lazy group nor a prefix value can leave the command value (neither
consumes an unescaped double quote), so the description cannot satisfy it.

What it counts follows the scripts of the two templates, read from their package.json at the pinned commits of
evals/lz-tdd-apply/templates.json: the kata has `test:jest`, `test:jest:watch`, `test:mocha` and `test:vitest`;
srvx has `test`, four `test:node-*` scripts and `vitest` (`"vitest": "vitest"`). `Bash(npm run:*)` in the eight
suites permits all of them and all are counted. Not counted:

- ways to start a runner that the allow list of the apply suites refuses (it permits `Bash(npx vitest:*)
  Bash(npm test:*) Bash(npm run:*) Bash(cd:*)`): pnpm, yarn, a path into node_modules, `time`, `timeout`;
- srvx's `npm run dev` (vitest in watch mode), which the allow list permits. The committed pattern does not count
  that command either;
- a flag between `npm run` and the script name (`npm run --silent test:jest`), which the allow list permits and the
  committed pattern counted. No saved run depends on it: the re-grade below changes exactly two verdicts, both
  listings.

Known limit, not changed by this plan and not measured on the saved runs: the kata has no `test` script, so
`npm test` in a kata workspace ends with npm's missing-script error and still counts, because a command that ran
and exited non-zero is a call that took effect.
