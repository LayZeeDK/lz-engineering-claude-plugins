## Critical Issues

### CR-01: Slim graders and scaffold scripts are read from the working tree at run time, after the uncommitted-cases check

**File:** `tools/evals/slim.ts:255`, `tools/evals/slim.ts:404`, `tools/evals/slim.ts:426`, `tools/evals/eval.ts:249`, `tools/evals/eval.ts:325`
**Issue:** `refuseUncommittedCases` (eval.ts:249) checks `evals/lz-tdd` and `evals/lz-tdd-apply` once, when the
process starts. After that:

- `graded()` (slim.ts:255) calls `readGraders(run.caseInfo.dir)` from the working tree when each session ends.
- `startSlimRun` reads `case.yaml` (`scaffoldScript`, slim.ts:404) and runs the script file from the working tree
  (slim.ts:426) when each run starts.
- `result.json` records `casesTree` from HEAD at staging time (eval.ts:116-121).

The comment at slim.ts:247-248 says the graders "equal HEAD because `run` refuses uncommitted cases", but that is
true only at the moment the process started. Failure scenario: Lars starts `run` on `baseline-22.1` (hours of
paid slim sessions, one at a time), then fixes a grader in the same checkout while the runs go on, the way
552718f fixed `edited-test.md`. Every slim run that ends after the edit is graded with the new, uncommitted
grader, while its `result.json` claims the old `casesTree`. `aggregate` sees one tree per arm and reports
mixed-grader numbers as one cell, with no warning. A scaffold script edited mid-run changes the starting state
of later runs in the same way. eval.ts:325 already parses every slim run's graders before the first spawn,
then throws the result away.
**Fix:** Snapshot the case inputs when the check passes and use only the snapshot from then on. Keep the graders
eval.ts:325 already reads, and the scaffold script bytes, per run:
```ts
// eval.ts, before staging
const graderSets = new Map(todo.filter(isSlim).map((run) => [run.runDir, readGraders(run.caseInfo.dir)]));
const scaffolds = new Map(todo.filter(isSlim).map((run) => {
  const script = scaffoldScript(run.caseInfo.dir);
  return [run.runDir, script === null ? null : readFileSync(script)];
}));
// pass both in SlimContext; graded() uses ctx.graders.get(run.runDir), and runScaffold writes the
// snapshot bytes to a temp file (or <rawDir>/scaffold.sh) and runs that file instead of the case file.
```
Reading both from `HEAD:` with `git show` works too, and also makes them match `casesTree` by construction.

## Warnings

### WR-01: A tool_used grader counts failed and denied calls as if they happened

**File:** `tools/evals/grade.ts:113-119`, `tools/evals/trace.ts:182-203`
**Issue:** `passes()` counts every `tool_use` block whose name and input match, whatever its result.
`toolCalls()` computes `isError` and `denied` for each call, but no grader reads either field (the only
readers are the tests and object literals). Failure scenarios with the committed graders:
`apply-lz-red-srvx-r1/graders/edited-test.md` (`tool: 'Edit|Write'`, min 1) passes on an `Edit` that failed
with "String to replace not found" and changed nothing. `production-untouched-edit.md` (max 0) fails a run whose
only `src/` Edit was refused by the permission layer and also changed nothing. `ran-tests.md` passes on a `Bash`
call the allow list denied. The grader descriptions ("The red step edited or created a test file") claim an
effect the grader does not check, so pass rates on the slim suites skew in both directions. For crosscheck
parity on plugin-eval suites the model has to match the CLI's semantics, but slim suites are graded only by the
harness, so it decides what a call means there.
**Fix:** For slim suites, count only calls that took effect, and keep plugin-eval behaviour for crosscheck:
```ts
const effective = (call: ToolCall): boolean => !call.denied && !call.isError;
const count = evidence.calls.filter(
  (call) => tools.includes(call.name) && (!onlyEffective || effective(call)) && (inputMatch === null || inputMatch.test(JSON.stringify(call.input ?? null))),
).length;
```
Pass `onlyEffective` from the suite backend (slim: true), or add an explicit grader key such as
`count: succeeded` and require it in slim graders through check-cases. Add fixtures with a failed and a denied
call.

### WR-02: The shared stage folder's lz-tdd/ is rebuilt in place whenever HEAD's case trees change

**File:** `tools/evals/stage.ts:160-161`, `tools/evals/stage.ts:188-191`, `tools/evals/grade.ts:250`
**Issue:** `stageRef` keys the stage by commit only (`<stage root>/<sha12>`), and rebuilds `<stage>/lz-tdd` with
`rmSync(target)` + `renameSync(tmp, target)` whenever `casesTree(repo)` (HEAD) differs from `stage.json`. Two
failures follow:
1. Concurrency: process A is working through plugin-eval runs against `<stage>/lz-tdd` (the `--case` target).
   Lars commits a case change and starts process B on another run set with the same ref. B stages before it
   waits for the heavy lock (eval.ts:329 runs before `withHeavyLock`), deletes the folder A's live
   `claude plugin eval` reads from, and replaces it with new cases. A's in-flight run can fail on missing files,
   and A's later runs test B's cases while their `result.json` records A's `casesTree`.
2. Crosscheck: `crosscheckRunSet` reads graders from `<stage>/lz-tdd/evals/<case>` (grade.ts:250) and never
   compares `stage.json`'s `casesTree` with the run's `result.json` `casesTree`. Once any later `run` or `stage`
   on that ref restages after a case commit, crosscheck grades old traces with new graders and reports the
   difference as a gap between the grader model and the CLI (or as "no modelled grader").
**Fix:** Make the case target immutable per case tree, for example `<stage>/lz-tdd-<sha256(casesTree).slice(0,12)>`,
and pass that folder as the plugin-eval target and record it. Never delete a case target that may be in use.
In crosscheck, read the graders from the folder that matches the result's `casesTree`, and mark the run
unchecked when that folder is missing.

### WR-03: The pre-spawn grader read does not compile regexes, so a bad pattern fails only after the session is paid for

**File:** `tools/evals/grade.ts:36-90`, `tools/evals/grade.ts:110`, `tools/evals/grade.ts:113`, `tools/evals/eval.ts:324-327`
**Issue:** eval.ts:324 reads every slim run's graders before the first spawn "so its graders must read now", but
`readGrader` only checks that `pattern`, `flags` and `input_match` are strings. `new RegExp(...)` runs in
`passes()` after the session has finished. Failure scenario: a grader with `flags: gu` (invalid with `u` plus an
unescaped `{` in the pattern) or an unbalanced `(` in `input_match` passes the pre-spawn read; every slim run of
that case pays for its whole session, then `graded()` turns the throw into `failed`, and there is no regrade
command, so the only way back is another paid `rerun` or `resume`. check-cases catches this through the fixture
requirement, but `run` does not run check-cases, and a working-tree edit after the last check slips through
(see CR-01).
**Fix:** Compile in `readGrader` so a bad grader fails at read time:
```ts
const compile = (key: string, source: string | null, flags = ''): void => {
  if (source === null) { return; }
  try { new RegExp(source, flags); } catch (error) { throw fail(`${key} is not a valid regex: ${error instanceof Error ? error.message : String(error)}`); }
};
compile('pattern', def.pattern, def.flags);
compile('input_match', def.inputMatch);
```
Also refuse `min > max` there, since such a grader can never pass.

### WR-04: A run-set selection naming an unknown case or tag silently plans nothing

**File:** `tools/evals/run-set.ts:280-285`, `tools/evals/run-set.ts:289-295`
**Issue:** `selection()` only checks the format of `cases` and `tags`; `planRuns` filters `listCases(suite)` with
them and never checks that every named case exists or that the selection matched anything. Failure scenario: a
run-set.json with `{"suite": "apply-lz-red", "cases": ["apply-lz-red-r01"]}` (a typo for `-r1`) or
`"tags": ["baselne"]` plans zero runs for that suite. `run` reports success, and `aggregate` counts `planned` from
the same shrunken plan, so RESULTS.md shows neither "partial" nor any sign that a suite is missing from the
baseline.
**Fix:** In `planRuns`, throw when a `select.cases` name is not in `listCases(suite)`, and when a selection
matches no case:
```ts
const all = listCases(suite);
const unknown = (select.cases ?? []).filter((name) => !all.some((c) => c.name === name));
if (unknown.length > 0) { throw new Error(`${runSet.name}: suite ${select.suite} has no cases ${unknown.join(', ')}`); }
const cases = all.filter((c) => selected(c, select));
if (cases.length === 0) { throw new Error(`${runSet.name}: suite ${select.suite} selection matches no case`); }
```

### WR-05: The default lock booking can exceed heavy-lock's 1440-minute cap, and rerun has already moved the runs aside when it fails

**File:** `tools/evals/eval.ts:295-296`, `tools/evals/eval.ts:362-366`, `tools/evals/slim.ts:349-353`
**Issue:** Without `--lock-minutes`, the booking is the sum of `timeoutMinutes + 2` over every run, including
plugin-eval runs that run `--concurrency` at a time, and nothing caps it. `heavy-lock.ts` refuses
`--minutes` above `MAX_MINUTES = 24 * 60` (heavy-lock.ts:19, :164). Failure scenario: `rerun` of 90 trigger
runs (default `timeoutMinutes` 15, so 1530 minutes), or any `run` of more than 84 such runs, reaches
`withHeavyLock`, whose acquire exits non-zero with a code other than 2 or 4, so the harness throws
`heavy-lock acquire exited 1`. For `rerun`, `setAside` (eval.ts:363) has already moved the named runs into
`set-aside-<n>`, so the error leaves the run set changed, against the comment at eval.ts:308 ("Every refusal
comes before the first spawn and before the lock is taken"). The sum also over-books by a factor of
`--concurrency` for plugin-eval runs, which holds the timing slot away from peers for no reason.
**Fix:** Compute the default as the plugin-eval part divided by concurrency plus the slim part, refuse before
`setAside` when it exceeds 1440 (naming `--lock-minutes` and splitting the run into parts as the way out), and
call `setAside` only inside the `withHeavyLock` callback, after the lock is held.

### WR-06: The `claude plugin eval` child has no timeout, so a hung CLI holds the timing slot forever

**File:** `tools/evals/plugin-eval.ts:283`, `tools/evals/run-set.ts:502-527`
**Issue:** Slim runs pass `--timeout-min` to run-slim, but `startPluginEvalRun` starts the CLI through
`spawnLogged`, which has no timer, and passes no timeout flag. `suite.timeoutMinutes` (default 15) is used for
the lock booking only. Failure scenario: one plugin-eval session stuck in a tool call (the exact case
`LZ_EVAL_STUB_HANG_AFTER` simulates, which the dry run ends by killing the process tree from outside) blocks its
worker for good. With `--concurrency 3`, the run set stops making progress once three runs hang, and the
heavy-lock timing slot stays held past its booked end, holding back every peer session's heavy work, until a
human notices.
**Fix:** Give `spawnLogged` an optional timeout that kills the child tree (on Windows `taskkill /PID <pid> /T /F`)
and settles the run as `failed` with the reason "timed out after N min"; pass
`run.suite.timeoutMinutes * 60_000` (plus a grace period for the judge) from `startPluginEvalRun`.

### WR-07: The with/without table pools every arm that has a plugin into one with side

**File:** `tools/evals/aggregate.ts:317-337`
**Issue:** `withWithout` builds the with side from every row of the suite with `run.ref !== null`, across all
arms, and the without side from every `ref === null` row across all arms. Per-arm grader counts exist
(`graderCounts`), but the discrimination verdict does not keep arms apart. Failure scenario: an A/B run set with
cells `head` (ref X) and `base` (ref Y) on the same suite, which is the obvious use of several cells, gets one
pooled with count of X and Y runs compared against the no-plugin arm; a regression in X is averaged away and the
suite can read "discriminates" on the strength of Y alone. Today's `baseline-22.1` avoids it only because its
two plugin arms (`head`, `srvx`) run disjoint suites.
**Fix:** Key the with side and the table rows by arm (`arm/model/grader`), and either compare each plugin arm
against the no-plugin arm(s) separately or refuse when two arms with refs share a suite.

## Info

### IN-01: Slim cost and tokens assume a resume continues one session, while grade.ts assumes it may fork

**File:** `tools/evals/slim.ts:182`, `tools/evals/slim.ts:232-238`, `tools/evals/grade.ts:147-153`
**Issue:** `normalizeSlim` takes `Math.max` over the parts for `costUsd` and tokens ("running totals of the
session every resume continues"), while `runEvidence` collects calls from every distinct session id because "a
resume may fork a new one". If a resume does start a new session whose cost counter begins at zero, `Math.max`
reports only the largest part, so a resumed run's cost is under-counted in RESULTS.md. This is inferred from the
two comments, not measured.
**Fix:** Sum per distinct session id (max within one session id, sum across ids), or measure once on a real
resume and record which behaviour holds.

### IN-02: Two processes can both take over a stale run-set lock

**File:** `tools/evals/run-set.ts:362-370`
**Issue:** On a stale lock, the code does `rmSync(file)` then `claim()`. If A and B both see the stale pid, A can
remove and claim, then B removes A's fresh lock and claims, and both proceed and pay for the same runs. The
window is narrow (two starts against one stale lock at the same moment).
**Fix:** Take the stale lock over by renaming it to a unique name first (`renameSync(file, `${file}.stale-${pid}`)`);
only the process whose rename succeeds goes on to `claim()`.

### IN-03: A run that throws before raw/ exists is reported as "see its raw/refused.txt", which was never written

**File:** `tools/evals/run-set.ts:484-489`, `tools/evals/eval.ts:147-149`, `tools/evals/plugin-eval.ts:260-266`
**Issue:** `runAll` turns a thrown error into `failed` without writing anything, but `reportOutcomes` points at
`raw/refused.txt`. Examples: `pluginEvalTarget` throwing for a plugin-eval suite in a `ref: null` cell (which
`stageRuns` also does not refuse up front), or `copyTemplate` refusing a non-empty folder. The error text goes to
stderr only.
**Fix:** Write the error to `raw/refused.txt` in the `runAll` catch (through `settleRun`), and refuse a
plugin-eval suite in a ref-less cell in `planRuns` or `stageRuns`.

### IN-04: Empty or relative root variables are taken as given

**File:** `tools/evals/eval.ts:244-246`, `tools/evals/slim.ts:61-63`
**Issue:** `LZ_EVAL_STAGE_ROOT=''` and `LZ_EVAL_SLIM_ROOT=''` pass `??`, so stage and template folders land at the
drive root (`/templates/...`), while `required()` treats an empty value as unset. A relative
`LZ_EVAL_STAGE_ROOT` gives a relative plugin folder, which `expandAllow` turns into `Read(/dist/eval/...)`, a rule
relative to the session's project instead of the `//` absolute form, so the session's reads of the plugin are
denied. run-slim resolves `--plugin-dir` itself, so the plugin still loads, and the run quietly measures a skill
that cannot read its references.
**Fix:** Treat `''` as unset (`||`) and `resolve()` the three roots once at startup.

### IN-05: writeRecheck can lower a count it says only grows

**File:** `tools/evals/eval.ts:158-166`
**Issue:** `{ ...before, ...listed }` lets a newly listed 5 replace a larger count already in recheck.json (for
example 7 set by hand), which removes runs from the plan and from the results counted.
**Fix:** Merge with `Math.max(before[key] ?? 0, listed[key])`.

### IN-06: The transcript folder name is computed in two places

**File:** `tools/evals/grade.ts:129`, `tools/evals/slim.ts:98-100`
**Issue:** `sessionTranscripts` repeats `projectFolder`'s regex. If one changes (Claude Code truncates and hashes
long names), the resume path and the grading path disagree on where a transcript is.
**Fix:** Import `projectFolder` in grade.ts (or move it to trace.ts, which both already import).

### IN-07: eval.test.ts and run-set.test.ts inherit LZ_EVAL_* variables from the shell

**File:** `tools/evals/eval.test.ts:38`, `tools/evals/run-set.test.ts:79`
**Issue:** Both spread `process.env` into the child, unlike dry-run.test.ts:59, which strips `LZ_EVAL_*` "so a
heavy lock or a real binary set in the shell never leaks in". A shell with `LZ_EVAL_STUB_HANG_AFTER`,
`LZ_EVAL_STUB_ERROR` or `LZ_EVAL_PROJECTS_DIR` set makes these tests hang or fail for reasons unrelated to the
code.
**Fix:** Filter `LZ_EVAL_` keys out of the inherited environment in both `evalCli` functions, as dry-run.test.ts
does.

### IN-08: The Skill-grader exclusion in aggregate reads today's working tree and matches by name across suites

**File:** `tools/evals/aggregate.ts:309-313`
**Issue:** `skillGraders` decides which verdicts leave the with/without table from the graders in the working tree
at aggregate time, not the ones that ran, and excludes a grader name from every suite once any suite has a Skill
grader of that name. A `Skill|X` tool value also escapes the `def.tool === 'Skill'` test.
**Fix:** Exclude per case directory (`dir + name`), and read the graders of the run's recorded `casesTree`.

### IN-09: The lint and the runtime disagree on what scaffold_script may be

**File:** `tools/evals/check-cases.ts:153`, `tools/evals/slim.ts:290`
**Issue:** check-cases accepts `.` and `..` (both match `^[A-Za-z0-9._-]+$` and exist) and refuses nested paths;
`scaffoldScript` refuses `.`/`..` and accepts nested paths. A case passes the lint and fails at run start, or the
other way round.
**Fix:** Have check-cases call `scaffoldScript(path)` and check that the file exists, so one rule applies.

### IN-10: The lockfile comes from the clone's working tree even when the pinned commit holds it

**File:** `tools/evals/templates.ts:367-369`
**Issue:** For a recipe without `from`, the archived lockfile at the pinned commit is overwritten with
`<clone>/<path>` from the clone's checkout. When the clone is checked out at another commit with a different
lockfile, the build fails the sha256 check although the pinned commit's own lockfile matches. It fails loudly,
so no wrong template results.
**Fix:** Read the lockfile with `git cat-file blob <commit>:<path>` when the commit has it, and fall back to the
working-tree file only for a lockfile the clone does not commit.

### IN-11: cleanEnv's temp HOME does not isolate Node.js children on Windows

**File:** `tools/evals/templates.ts:184-196`, `tools/evals/slim.ts:376-399`
**Issue:** Node's `os.homedir()` reads `USERPROFILE` on Windows and, when it is unset, falls back to the user's real
profile folder; `HOME` is ignored. The vitest, `npm run <build>` and scaffold children therefore still write npm
config, caches and tool state into Lars's real profile. The comments claim "a temp HOME". Secrets in the
environment are still dropped, so this is about the claim, not a leak.
**Fix:** Also set `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` to folders below the temp home on win32, or reword
the comments to say only Git Bash sees the temp HOME.

### IN-12: Generality without instantiation - denied and isError tool-call flags are computed and read by nothing

**File:** `tools/evals/trace.ts:172-201`
**Category:** necessity
**Issue:** `refusal()` parses the permission-denied text and `toolCalls()` sets `denied` and `isError` on every
call, but no production code reads either field: the only uses are in trace.test.ts, grade.test.ts and the
literal at check-cases.ts:308 (`rg '\.denied|\.isError'` over tools/evals). The parsing defends against nothing
today.
**Fix:** Either use the flags in grading (WR-01), or drop `refusal()` and both fields until a grader needs them.

### IN-13: The usage line omits the template command and the lock flags

**File:** `tools/evals/eval.ts:73-74`
**Issue:** The error text a wrong command line gets lists neither `template <name>` nor `--lock-minutes` /
`--lock-note`, which the header comment documents.
**Fix:** Add `| template <name>` and `[--lock-minutes <1-1440>] [--lock-note <text>]` to `usage`.

### IN-14: A case with no graders counts as a passing run in the recheck decision

**File:** `tools/evals/aggregate.ts:189`, `tools/evals/grade.ts:92-101`
**Issue:** `recheckCases` treats a run as passing when `facts.with.every(...)` holds, which is true for an empty
list; `readGraders` returns `[]` when a case has no `graders/` folder, and check-cases does not require one. Such
a case always "passes" on both models and never triggers the D-10 recheck.
**Fix:** Have check-cases require at least one grader per case, or treat an empty verdict list as not passing.
