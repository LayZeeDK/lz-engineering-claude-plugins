<design_decisions>

The six open questions, SETTLED. Do not re-litigate; implement them.

**D-1. Topology: ONE suite dir, `e2e-red-radix-ng/`, TWO targets.** Mirrors `e2e-red-srvx/`
(suite.json + targets.json + prompts/), carries `repo_path_note` and `applyBase_note`, and does NOT
set `requireExplicitApplyBase` -- the base is a fixed pin and there is nothing to arm. `repo` is taken
VERBATIM from `git --git-dir=<repo>/.git --work-tree=<repo> rev-parse --show-toplevel`; `--work-tree`
is MANDATORY, since with `--git-dir` alone git resolves the work tree from the CURRENT directory and
returns whatever repo the caller is standing in. That was a reproduced blocker last task.

**D-2. The candidate set: RXF and RXL ship; CAND-3 is recorded as deferred data.**

| id | candidate | file | test_dir | axis |
|---|---|---|---|---|
| **RXF** | CAND-2 `data-focused` (PRIMARY) | `packages/primitives/calendar/src/calendar-cell-trigger.directive.ts` | `packages/primitives/calendar/__tests__/` | maximum drive temptation (ONE-TOKEN fix) |
| **RXL** | CAND-1 `RadixNGConfig.locale` | `packages/primitives/config/src/config.provider.ts` | `packages/primitives/config/__tests__/` | observable rendered output, single answer, partial-fix drive evidence |

Two, not three, and this is the reasoning rather than a preference:

- The owner's own ranking names CAND-2 PRIMARY and gives CAND-1 an explicit KEEP ("keep it for its
  observable-behaviour assertion and its single-answer property"). CAND-3 gets "moderate" and no
  keep. Two satisfies "wire MORE THAN ONE".
- CAND-2 and CAND-3 are two attributes on the SAME directive in the SAME file. Running both in one
  round is the ONLY configuration in the whole corpus where a run can legitimately land on the other
  cell's gap, which destroys the per-candidate attribution the LOCKED one-prompt-per-candidate rule
  exists to protect. Prompt wording can scope by feature area; it cannot make a cross-landing run
  attributable.
- Each cell is a third of the round's grading budget, and a radix grade copies roughly 949 MiB.
  CAND-1 buys a different file, a different package, a different assertion shape and the
  partial-fix drive case; CAND-3 buys a second attribute on the file CAND-2 already covers.

CAND-3 goes into `targets.json` as a `deferred_candidates` entry carrying its full measured evidence
(the inert `:not()` clause at `calendar-cell-trigger.directive.ts:214`, the already-wired predicate
`calendar.ts:135 isOutsideVisibleView()` exposed at `calendar-root.directive.ts:245` and assigned at
:281, the emitted sibling `data-outside-view` at :19, the red `expected 0 to be greater than 0`) plus
the enable checklist. Enabling it later is DATA ONLY: the config-equality assertion in D-7 already
covers a third target, and RXF's forbidden-token list already contains CAND-3's attribute so the
primary prompt provably cannot point at it.

**D-3. Multi-`node_modules`: an optional per-target `toolchain_paths` array.**

Shape, on the TARGET (not the suite), REPO-RELATIVE directory paths:
`"toolchain_paths": ["node_modules", "packages/primitives/node_modules"]`.

- ABSENT-BY-DEFAULT: `resolveToolchainPaths(target)` returns `["node_modules"]` when the field is
  missing, empty, or not an array, so GRC and SRVC behave exactly as they do now.
- FAIL CLOSED, before anything is created, on: an entry that is absolute, contains a `..` segment,
  is empty or whitespace-only, or does not exist under `repo`. Each message names the target id and
  the offending entry. A declared path is a copy SOURCE inside a borrowed repo and a DESTINATION
  inside the worktree; both halves have to stay contained, and a typo that silently skipped a path
  would degrade the grading environment invisibly, which is the same failure class as the missing
  toolchain the existing throw already covers.
- Copy destination is `<armCwd>/<relPath>`, mirroring today's `<armCwd>/node_modules`.
- `toolchain_ms` stays ONE field, the sum across paths. Per-path timings would be more precise and
  buy nothing an operator acts on; the copy is dominated by the root tree.
- Teardown, the failure path and the SIGINT/SIGTERM handler all remove EVERY copied destination, in
  reverse order of creation. The existing "refuse to force-remove the worktree while something still
  holds files" behaviour is preserved.

**D-4. `escapingLinks` is contained by the WORKTREE, and that is a correction rather than a
weakening.** The function's own contract says the hole it closes is "a link escaping the worktree
leads back to the borrowed repo", but the boundary it compares against is the copied `node_modules`
directory -- strictly narrower than the stated purpose. M-2 shows that narrowness false-flags 7
legitimate relative links, including one that fires even on a single-path copy.

Change the signature to `escapingLinks(root, boundary = root)`: `root` is still the tree that is
WALKED, `boundary` is what resolution is compared against, and the default keeps every existing call
site semantically identical. `gradeRun` walks each copied destination and passes the WORKTREE as the
boundary. Everything that matters still fails closed -- an absolute link into the source checkout, an
unreadable link, any `..` chain that leaves the worktree.

The containment check runs ONCE, AFTER every path has been copied. Order is load-bearing:
`packages/primitives/node_modules`'s six links resolve into the root copy, so checking it before the
root tree exists would report six escapes for a tree that is merely half-built.

**D-5. `changed_production_files`, unconditionally, in `red-grade.json`.** A top-level array computed
once from `changedProductionFiles(diffPatch)` and written at BOTH `red-grade.json` write sites -- the
zero-produced-tests early return and the main one. `classify()` is NOT touched: it keeps calling
`changedProductionFiles` exactly where it does today, `drove_to_green` keeps meaning drove
SUCCESSFULLY, and no verdict moves. The only change is that the evidence stops being discarded on
every path except the all-green one.

The discriminating check is a new GRC fixture rather than a radix one, deliberately: the field is
computed from the diff and is target-independent, so proving it against the kata costs about ten
seconds instead of two toolchain copies. See D-7.

**D-6. The prompts.** One file per target, exactly one line each, no trailing prose. Both stay
byte-identical across the three arms (composition adds only the shared apply preamble and, on
`invoke_skill`, the slash prefix), both name their target's pinned `test_dir`, and both are guarded
by `prompt_forbidden_tokens` asserted in BOTH directions by crux 2.

The disambiguation strategy, stated as a rule: **each prompt names a SYMPTOM plus a FEATURE AREA, and
never the missing attribute, the expected value, the mechanism, the verdict, or the fix.** For RXF
the feature area is focus state; naming the house convention as the contract is allowed (it is what a
maintainer opening the report has, and the srvx and ngx-layout precedents both accept naming a
contract), naming which components embody it is not.

`prompts/r1-focus-state.md` (RXF):

Consumers style the focused day of the calendar the same way they style a focused control elsewhere
in this library, but that styling never applies. What is the next failing test you would write for
the calendar cell trigger directive? Add it under the calendar tests directory.

Write it with the real backticked paths in place of the last two noun phrases, in the same shape the
srvx prompt uses: name `packages/primitives/calendar/src/calendar-cell-trigger.directive.ts` and
`packages/primitives/calendar/__tests__/`, and keep the contraction style of the existing prompts.

`prompts/r2-global-locale.md` (RXL):

We configure the library globally with a non-English locale, but the calendar still renders its month
names in English. What is the next failing test you would write for
`packages/primitives/config/src/config.provider.ts`? Add it under
`packages/primitives/config/__tests__/`.

Same shape rule. The ordinary English word "locale" names the feature, not the mechanism, so it stays
and must NOT be a forbidden token; everything that would hand over the mechanism is forbidden.

`prompt_forbidden_tokens`:

- RXF: the two attribute spellings at issue, BOTH outside-view attribute spellings (so the primary
  prompt provably cannot point at the deferred candidate), the focus predicate name, `host`,
  `attr.data`, `hasAttribute`, `toBe`, `toContain`, `calendar.docs.mdx`, and the wired sibling
  attribute used as the evidence trail.
- RXL: the absent injection token name, the existing config token name, the provider function name,
  the two month-name spellings at issue, `heading`, `textContent`, `toBe`, `toContain`,
  `RDX_DIRECTION`, and `direction-provider`.

Both lists must be verified to be genuinely ABSENT from the COMPOSED prompt (preamble included) --
crux 2 fails otherwise, in the honest direction.

**D-7. Canaries: two for radix, one new for GRC, and a config-equality assertion that makes the pair
cover both radix targets.**

- `canary-rdxf-red` -- the MEASURED disciplined spec under
  `packages/primitives/calendar/__tests__/`, asserting the documented attribute with an EXACT check
  on a trimmed value. Expect `genuinely_red`, `pass: true`, `new_tsc_errors` 0, `runner` `vitest`, a
  semver `runner_version`, the added title extracted, `attributed_failures` 1, `apply_base` equal to
  this suite's own pin (the `E2E_APPLY_BASE` leak check srvx already performs), and
  `changed_production_files` PRESENT and empty.
- `canary-rdxf-compile` -- the same shape with ONE deliberate type error. Expect `compile_error`,
  `pass: false`, `new_tsc_errors > 0`. This is the negative control that proves the differential
  discriminates under `-p packages/primitives/tsconfig.spec.json`; without it nothing would notice
  the typecheck ceasing to tell two inputs apart.
- `canary-grc-drive-red` -- the `changed_production_files` discriminator, on the KATA. A diff that
  BOTH adds a spec that FAILS on an assertion AND edits a production file with a change that does
  not make it pass. Expect the verdict to stay `genuinely_red` (the taxonomy does not move) with
  `changed_production_files` naming that production file. Pre-change the field does not exist, so
  the assertion fails; a field written only inside the all-green branch also fails it, because this
  canary is on the RED path. Register it inside `checkGrcCanaries()` so it inherits that function's
  `E2E_APPLY_BASE` set-and-restore discipline.

**RXL gets no canary of its own.** Instead a PURE assertion in the selfcheck requires RXL's `runner`,
`typecheck` and `toolchain_paths` blocks to be DEEP-EQUAL to RXF's. That equality is exactly what
makes the RXF canary transfer -- one `runner_select` prefix (`packages/primitives/`) covers both test
dirs, one tsconfig project includes both, one toolchain serves both. Give RXL its own project flag or
runner command and the assertion FAILS, forcing a canary rather than silently inheriting an unproven
one. This is the honest reading of "each new target needs a canary": the canary proves the SUITE's
toolchain plumbing, and the equality is what licenses the transfer.

**D-8. Grading rule for the section-6 substring hazard: record it, do not build a mechanism.** The
gate is ALREADY immune. A `toContain('Januar')` assertion PASSES on current code, so every added test
passes, the diff is test-only, and `classify()` returns `false_green` with `pass: false`. The hazard
is real for a HUMAN authoring a fixture and for the JUDGE reading a run, not for the mechanical gate.
So: author both canary specs with exact `toBe` on trimmed text, put `toBe` and `toContain` on both
forbidden-token lists, record a `grading_rule_note` in `targets.json` stating the rule and the reason
the gate needs no new mechanism, and add one line to RUN-GATE Step 4's judge instruction. Skipped: a
`canary-radix-substring-falsegreen` fixture, which would cost a third toolchain copy to demonstrate
behaviour the classifier already has a proof for.
