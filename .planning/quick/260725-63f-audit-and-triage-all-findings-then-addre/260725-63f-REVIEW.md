### CR-01: the node_modules junction turns `git apply` into a write path into the borrowed repo

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:570` (junction creation) and `:618` (`git apply`)

**Issue.** The junction is created at `:570`, before `git apply` runs at `:618`. `diff.patch` is
explicitly declared attacker-shaped input by this task's own threat model ("captured runDir ->
gradeRun: meta.json and diff.patch are attacker-shaped inputs relative to the grader"), and nothing
between those two lines constrains which paths the patch may touch. Any hunk under
`TypeScript/node_modules/...` therefore traverses the junction and lands in the borrowed kata's real
`node_modules`.

T-63f-01 only reasoned about the DELETION direction (teardown following the link). The WRITE
direction was not considered at all. Before this change the risk did not exist: a fresh worktree had
no `node_modules`, so such a patch created a throwaway directory under `%TEMP%`.

**MEASURED** (throwaway repo, junction to a scratch stand-in, never the kata):

```
git apply (modify hunk on TypeScript/node_modules/typescript/KEEP.txt)
  -> exit 0; the file in the LINK TARGET now reads "PWNED2"
git apply (new-file hunk on TypeScript/node_modules/.bin/EVIL.txt)
  -> exit 0; the file was CREATED in the link target
```

Only the "new file over an existing path" variant is blocked, and only by `already exists in working
directory`, which is not a security control.

**Concrete failure scenario.** The metered fan-out grades 9 captured runs. One model, told to add a
failing test, also runs `npm install --save-dev @types/foo` in its apply checkout and stages the
result with `git add -f`, or simply writes a helper into `node_modules/.bin`. `run-e2e.mjs` captures
that in `diff.patch`. `gradeRun` then applies it straight into
`D:/projects/github/emilybache/GildedRose-Refactoring-Kata/TypeScript/node_modules`, silently
corrupting a third-party checkout the project promised to leave pristine. The canary's
`fs.existsSync(realNodeModules)` assertion does not catch this -- the directory still exists.

**Fix** (fail closed before the junction exists, using the helper already in this file):

```js
// A captured diff must never reach the target's real node_modules through the junction below.
const throughLink = changedPaths(diffPatch).find((p) => /(^|\/)node_modules(\/|$)/.test(p));

if (throughLink) {
  throw new Error(
    `grade-red: the captured diff touches '${throughLink}', which would be applied THROUGH the ` +
      "node_modules junction into the target's real dependency tree (fail closed, T-63f-01)",
  );
}
```

Place it next to the existing `nodeModulesSrc` existence check at `:535`, before
`git worktree add`.

### CR-02: the no-tests widening classifies on model-controlled text, so a crashed runner is scored

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:250-274` (specifically `:258`, `:260`, `:270`)

**Issue.** `parseRunnerReport` tests `NO_TESTS_RE` against `stdout + "\n" + stderr` in full. On both
runners' error paths that text includes a CODE FRAME echoing the produced spec's own source. The
recognition signal is therefore not runner-authored -- the model under test can put it there.

`NO_TESTS_RE` was written to disambiguate a suite-level message INSIDE already-parsed JSON, where
the text is runner-authored. Reusing it verbatim to gate a fail-closed path over raw process output
silently widened its trust boundary.

**MEASURED** (detached kata worktree with the junction, torn down; spec content is the only variable):

```
case           exit  stdoutBytes  parseRunnerJson  NO_TESTS_RE(combined)  outcome
exit-hard-jest    0            0  THROWS           true                   *** SYNTHESIZES no_tests ***
   matched line: "1 | // no tests found"
exit-hard-vitest  1            0  THROWS           false                  throws (fail closed)
```

The `exit-hard-jest` spec is two lines: a comment reading `// no tests found` and
`process.exit(0);`. jest is killed before it writes a byte of JSON and exits 0. The ONLY thing in
the combined output matching `NO_TESTS_RE` is jest's own echo of the spec's comment. Pre-change this
threw (correct: the runner produced nothing usable). Post-change it emits a `no_tests` verdict with
`pass:false`, `runner_version` populated, and `red-grade.json` written -- a hard runner crash
laundered into a scored measurement.

Two aggravators in the same function:
- `runRes.status` and `runRes.error` are never inspected (`:631-638`). A spawn failure (`ENOENT`) or
  a `maxBuffer` overflow (`ENOBUFS`, which TRUNCATES stdout) reaches the same branch, and whether it
  throws or becomes a verdict depends on incidental text.
- On truncation the truncated JSON payload itself joins `combined`. Jest's `--json` payload contains
  every test's `fullName` and `failureMessages`, i.e. more model-authored text.

**Fix.** Recognize only the runner's own sentinel LINE, and require the run to actually have produced
nothing:

```js
// The runner's OWN sentinel line, anchored -- not an echo of the produced spec's source.
const NO_COLLECT_SENTINEL = /^no tests? (?:files? )?found, exiting with code \d+$/i;
...
const lines = combined.split('\n').map((l) => l.trim());
const observed = lines.find((l) => NO_COLLECT_SENTINEL.test(l));

if (!observed || stdout.trim() !== '' || runRes.error) {
  throw err;
}
```

**MEASURED discrimination** of the anchored form (`ANCHORED` column):

```
"No tests found, exiting with code 1"                             NO_TESTS_RE=true  ANCHORED=true
"No test files found, exiting with code 1"                        NO_TESTS_RE=true  ANCHORED=true
"      1 | // no tests found"                                     NO_TESTS_RE=true  ANCHORED=false
"    at Object.<anonymous> (test/jest/x.spec.ts:1:1) no tests..."  NO_TESTS_RE=true  ANCHORED=false
```

`canary-nocollect` keeps passing under the anchored form: its observed line is verbatim
`No tests found, exiting with code 1` (printed by the current battery run).

### IM-01: the Rule-2 TS5xxx/TS6xxx guard false-positives on ordinary source diagnostics

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:609`

```js
const configError = [...baseErrors].find((l) => /error TS(?:5\d{3}|6\d{3})\b/.test(l));
```

**Issue.** TS6xxx is not an option/config range. It is TypeScript's general "message" range and it
contains ordinary, file-scoped diagnostics: TS6133 (declared but never read), TS6138, TS6192 (all
imports unused), TS6196, TS6198, TS6205, TS6059 (not under rootDir), TS6053 (file not found). Those
are emitted with a `file(line,col):` prefix and do NOT abort the compile.

**MEASURED** with the kata's own tsc 4.9.5:

```
$ tsc --noEmit --strict --noUnusedLocals --noUnusedParameters probe.ts
   GUARD FIRES -> probe.ts(1,1): error TS6192: All imports in import declaration are unused.
   GUARD FIRES -> probe.ts(4,9): error TS6133: 'unusedLocal' is declared but its value is never read.
   GUARD FIRES -> probe.ts(5,10): error TS6133: 'a' is declared but its value is never read.
```

**Concrete failure scenario.** It cannot fire on GRC today -- the kata's baseline codes are
`{TS2691:5, TS2403:7, TS1383:8, TS2420:1}` (MEASURED). But `targets.json` and grade-red's own
comments describe the gate as target-agnostic, and `noUnusedLocals` is in the stock `tsc --init`
template. The moment a second target repo sets it and has one unused local anywhere in its
pre-existing source, EVERY grade for that target aborts with the message "the target typecheck
failed at the option/config layer" -- which is false, and which fails closed in a way the operator
cannot act on.

**Fix.** Discriminate on the shape, not just the code. Genuine option-level diagnostics either carry
no file prefix at all (`error TS6046: ...`, `error TS5023: ...`) or are anchored at the tsconfig:

```js
const configError = [...baseErrors].find(
  (l) => /error TS(?:5\d{3}|6\d{3})\b/.test(l) && (!/^\S+\(\d+,\d+\):/.test(l) || /^[^(]*tsconfig[^(]*\(/i.test(l)),
);
```

MEASURED against this session's data: rejects the three TS6133/TS6192 lines above, still accepts
`error TS6046: Argument for '--lib' option must be: ...` and the global-tsc
`tsconfig.json(4,15): error TS5107: ...`.

### IM-03: teardown swallows a real junction-removal failure and then force-removes the worktree anyway

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:555-564`

```js
if (linkCreated) {
  try {
    fs.rmSync(nodeModulesLink, { recursive: true, force: true });
  } catch {
    // best-effort; the worktree removal below still has to run
  }
}

git(gitRoot, ['worktree', 'remove', '--force', worktree]);
```

**Issue.** The stated purpose of the `catch` (per the comment and the plan) is "so an already-gone
link cannot mask the real error". But `force: true` ALREADY suppresses `ENOENT`. The catch therefore
fires only when removal genuinely failed -- `EPERM` / `EBUSY` from an antivirus or search indexer
holding a handle on a 300-entry junction target, which is a routine Windows condition. That is
precisely the case where the code then proceeds to `git worktree remove --force` with the link still
live, voiding the ordering guarantee the comment above it asserts. The try/catch is inverted relative
to its documented intent.

`git worktree remove`'s exit status is also discarded (`git()` is called without `mustSucceed`), so a
failed removal is completely silent.

**MEASURED mitigating fact** (throwaway repo, junction to a scratch sentinel): on this platform
nothing follows a junction --

```
A: git worktree remove --force  with the junction still live  -> sentinel SURVIVES
B: fs.rmSync(junction, {recursive, force})                    -> link gone, sentinel SURVIVES
C: fs.rmSync(worktree-containing-live-junction, {recursive})  -> sentinel SURVIVES
D: rm -rf worktree-containing-live-junction  (Git Bash)       -> sentinel SURVIVES
```

So today this is a silent LEAK (a live junction into the borrowed repo left under `%TEMP%`, plus an
orphaned worktree), not a deletion. That materially de-risks T-63f-01 -- and it also means the
ordering the code treats as load-bearing is belt-and-braces rather than the sole protection.

**Fix.** Invert the tolerance: if the link removal genuinely fails, do NOT force-remove the worktree;
throw an operator-actionable error naming the link path so a human unlinks it.

```js
if (linkCreated) {
  try {
    fs.rmSync(nodeModulesLink, { recursive: true, force: true });   // force already tolerates ENOENT
  } catch (err) {
    throw new Error(
      `grade-red: could not unlink ${nodeModulesLink} (${err.code}). NOT removing the worktree -- ` +
        'remove the junction by hand first so no recursive delete can reach the target repo.',
    );
  }
}
```

### IM-04: no crash-safety for the junction; an interrupted fan-out strands a live link into the borrowed repo

**File:** `.claude/skills/lz-red-workspace/grade-red.mjs:545-570`

**Issue.** `teardown()` runs only via `finally`. `Ctrl-C`, a `SIGTERM`, an OOM kill, or a terminal
close between `:570` (junction created) and `:659` (finally) leaves a live junction to the borrowed
repo's real `node_modules` sitting under `%TEMP%`. There is no `process.on('exit'|'SIGINT')` handler
and no startup sweep of stale `red-wt-*` directories. Interrupting a 9-run metered fan-out is a
normal operator action, not an exotic one.

Per the MEASURED matrix in IM-03, git / `fs.rmSync` / coreutils `rm -rf` all refuse to follow the
junction, so the residual is bounded. It is not zero: Windows PowerShell 5.1's `Remove-Item -Recurse`
famously follows reparse points, `del /s` follows, and third-party temp cleaners vary.

**Fix.** Two lines: register `process.once('SIGINT', teardown)` / `process.once('exit', ...)` around
the try, and have the canary crux (or gradeRun startup) refuse to run when a stale
`os.tmpdir()/red-wt-*` directory already exists.
