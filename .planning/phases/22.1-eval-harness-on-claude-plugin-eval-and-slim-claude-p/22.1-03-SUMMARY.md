# Phase 22.1 Plan 03: Case lint, generated trigger and routing suites, and the pilot cases Summary

**`check-cases.ts` now ends `npm run check` and holds every committed case to the loader's keys, the twin rule, the
hygiene rules and a pass/fail fixture per grader definition. `port-cases.ts` turned today's trigger and routing sets
into 103 cases with record and baseline tags, and the pilot has its doing, probe and slim apply cases.**

## Accomplishments

- `check-cases.ts` (EVH-12): `lintCases(repo)` and `graderKey(def)`. It walks the suites under `evals/lz-tdd` and
  `evals/lz-tdd-apply` and checks each case folder. The rules: names start with `<suite>-` and are unique across
  suites; prompt.md uses only the 16 loader keys, minus `model` and `runs`; a `scaffold_script` exists; a slim
  suite's `target` is in templates.json; graders read under `readGrader`; invoke twins match their natural case.
  It grades every `evals/fixtures/graders/*.json` with `gradeRun` and requires one fixture per grader key. It scans
  every file `git ls-files --cached --others --exclude-standard -- evals` lists for non-ASCII bytes, any
  email-shaped token other than the public contact, and absolute paths outside `D:/tmp/` (drive paths in either
  slash form, and rooted `/home/`, `/Users/`, `/root/`, `/mnt/`, `/tmp/`, `/<letter>/`). `npm run check` ends with
  `node check-cases.ts`.
- `port-cases.ts` (D-11, D-12, D-13): `triggerCases`, `routingCases`, `writeSuite` and the command line that
  regenerates the four suites. Trigger tags: `trigger`, the skill, `fire`/`quiet`, `forward`, `heldout`, `chunk`,
  `canary`, `rec-<sha7>`, `baseline`. Fire cases grade `skill-fired` plus `sibling-quiet-<sibling>` for the other
  two skills. Quiet cases grade `quiet`. Routing cases grade `owner-fired` and `quiet-<skill>` for each skill that is
  neither the owner nor its second hop.
- Pilot cases: `doing-lz-red-08` comes from lz-red eval 8 and has a scaffold that writes `package.json` and an
  `isPalindrome` returning `false`. Its graders are skill-fired, wrote-test, the two production-untouched checks and
  red-line, and `doing-lz-red-invoke-08` is its twin. `harness-probes-write-inside` and `-write-outside` cover A1
  and A2. `apply-lz-red-r1` is heavy, runs on `gilded-rose-ts-armed`, and its body is the recorded apply preamble
  followed by the r1 prompt. `apply-lz-red-invoke-r1` is its twin.
- 16 fixtures, one per distinct definition: Skill fired and quiet for each of the three skills; Write on
  is-palindrome.test.ts; the Edit and Write quiet checks on is-palindrome.ts and app/gilded-rose.ts; the vitest
  spec Write; ran-tests; red-line; wrote-inside; asked-outside.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `asked-outside` grades `min: 1`, not `min: 0`**
- **Found during:** Task 3
- **Issue:** A `tool_used` grader with `min: 0` and no `max` passes on every run. It cannot record whether the agent
  tried, and its known-fail fixture would pass, which D-14 and the lint refuse.
- **Fix:** Default `min` (1). The grader passes when the agent tried to Write `outside.txt` and fails when it did
  not; Plan 04 still checks on disk whether the file appeared.
- **Files:** evals/lz-tdd/harness-probes/harness-probes-write-outside/graders/asked-outside.md,
  evals/fixtures/graders/asked-outside.json
- **Commit:** db414e5

**2. [Rule 3 - Blocking] The Task 3 stub slim run did not take the shared heavy lock**
- **Found during:** Task 3
- **Issue:** The plan sets `LZ_EVAL_HEAVY_LOCK` and `LZ_EVAL_LOCK_OWNER=gsd-22.1-03`, so the heavy suite would join
  the shared queue (held by a peer at the time). Under the shared-machine rule 2, a stub run (no model session, no
  timing) is light work that must not book the lock. The coordinator's message also said this plan needs no lock
  of its own. The harness, though, refuses a heavy suite without the lock variables.
- **Fix:** The run used a scratch clone of this branch with one local commit setting `heavy` to false. The case
  body, graders, template, slim root and run path were unchanged; only the lock wrapper was skipped. Plan 01/02
  tests cover the lock path. Nothing from the clone was pushed or merged.
- **Commit:** none (verification only)

**3. [Rule 3 - Blocking] Fixture paths under `D:\tmp\`**
- The plan's example fixture path `C:\\w\\src\\...` would fail the lint's own absolute-path rule, so every fixture
  path is under `D:\tmp\w\` (JSON-encoded backslashes, Pitfall 5).

**4. [Rule 1 - Bug] A plan acceptance command could not fail**
- `xargs rg -L '^tags: .*\bheldout\b'` uses `-L`, which in ripgrep is `--follow`, not "files without match". Also,
  `rg -l` prints Windows paths whose backslashes xargs strips. The check ran with `rg -l --path-separator //` and
  `--files-without-match`: 0 (control 10).

**5. [Rule 2 - Correctness] Lint rules beyond the behaviour list**
- Added: a case folder without prompt.md; a twin case with no natural case; a second fixture for one grader
  definition; a slim suite with no target; rooted POSIX paths. A fixture's `grader` takes GraderDef field names
  (`inputMatch`), and missing fields take `readGrader`'s defaults.

**6. [Rule 3 - Structure] Small choices the plan left open**
- Routing tags: `routing`, `owner-<owner>` (`owner-none` for c9) and `second-hop-<skill>` on c4.
- lz-tpp's chunk files come from `git ls-files` on `d07-chunks/` (the 9 tracked files), sorted.
- `triggerCases` takes an optional `TriggerSpec` (files and recorded set), so unit tests run on temp repositories.
  `triggerSpec` and `skills` are exported beyond the plan's lists.
- Suite literals in five test files gained `skill: null`.
- The prompt.md of each apply case has only `tags` in its frontmatter (slim runs read no turn or tool keys).
