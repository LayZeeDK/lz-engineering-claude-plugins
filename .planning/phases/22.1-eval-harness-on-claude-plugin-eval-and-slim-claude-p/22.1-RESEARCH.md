#### Resumability (the gate before any paid run)
- **D-01:** Copy lz-gardener's resume model (`D:/projects/github/LayZeeDK/lz-gardener/tools/evals/eval-run.ts`,
  `slim-output.ts`); lz-oop's harness has no resume code (searched 2026-11-24), so lz-gardener is the closer fit Lars
  asked the research to pick. The rules carried over: a run whose result file exists is done and is never started
  again; `run` starts only runs without a result, so raising n adds runs and keeps the old ones; `resume <run dir>`
  continues a stopped slim session with `run-slim.ts --resume <session id>` into `result-resume-<n>.json` beside the
  first result; `rerun <run dir>` moves the old run into a `set-aside-<n>` folder and starts it fresh; a session ended

  outputs but no result is a run that died and is refused by `run` until rerun. -- **Reversibility:** costly -- every
  later round's run sets assume this layout.
- **D-02:** `claude plugin eval` has no resume or session option (`claude plugin eval --help`, 2.1.327), so its unit

  <run set>/<arm>/<model>/<case>/run-<k>/ --json <same dir>/result.json --no-publish`. A finished `result.json` is a
  finished run; a stopped invocation loses at most its own run, which is "resume where its tool allows" for
  `plugin eval`. The harness aggregates the per-run results itself instead of relying on one invocation's report.
- **D-03:** "Shown working on a dry run" is two steps. First a free dry run: the run-set logic runs against a stub

## Summary

The harness splits by backend. `claude plugin eval` runs trigger, answer and no-shell doing cases. It has no resume
option, so the harness invokes it once per arm x model x case x run (D-02) and keeps its own run-set state.
lz-gardener's `eval-run.ts` already implements the resume rules D-01 names (done = result file, set-aside reruns,
refusal of a died run, usage-limit-as-failure) in tested erasable TypeScript, and most of its pure functions carry
over with a second backend added beside slim.

The most important measured fact: `plugin eval`'s `aggregate-result.json` does not say which model ran and has no
session id. `suite.modelOverride` only echoes `--model`. The per-run `trace.jsonl` that each run's `tracePath`
names does carry both (`system/init.model`, `result.modelUsage`, `session_id`, `total_cost_usd`). It sits in a temp
folder that is not always kept, so the harness copies it into the run folder right after each invocation. That is
how D-10 is met on the plugin-eval side. On the slim side, run-slim's `--out` file holds the
`--output-format json` result object, which has `modelUsage`, `total_cost_usd`, `session_id` and `num_turns`.

Two D-09 retirements conflict with the battery D-09 keeps. `selfcheck-routing.mjs` and `selfcheck-red.mjs` import
from `e2e-nx/run-e2e.mjs`, `grade-routing.mjs` and `grade-red.mjs`. `extract-samples.mjs` is not an eval runner: it
is the compile gate both workspaces run as `npm run typecheck`. The recommendation is to keep those files as
battery in this phase (see Open Questions 1-2).

**Primary recommendation:** Build `tools/evals/` by porting lz-gardener's run-set core and adding a plugin-eval
backend that copies each run's trace and writes `result.json` only after the run is complete, not limit-stopped,
and on the requested model. Prove it on a stub dry run. Then run one deliberately interrupted pilot that also
settles the three open unknowns: Write/Edit under `plugin eval` on native Windows, a scaffolded real-repo case,
and per-run cost.

  for a read-only case `["Task","Glob","Grep","Read","Skill","TaskStop","ToolSearch"]`; skills list = built-ins plus

### Pattern 1: done means `result.json`, written last by the harness

**What:** each backend writes to its own raw files (`plugin-eval.json` + traces, or `outputs/result.json` from
run-slim). The harness writes `result.json` at the run-folder root only after three checks pass: the run is
complete (not `partial`, no `error` of the API, limit or interrupt kind), it was not limit-stopped, and the trace
models match the model asked for. A run folder with raw files and no `result.json` is a died or failed run, and
`run` refuses it until `rerun` (D-01). This keeps one done-marker across both backends, and a usage-limit run can
never read as done.
**Example (from lz-gardener `eval-run.ts:216-219`, adapted):**
```typescript
// A run with a result is done; `run` starts the others, so raising n keeps the runs done.
export function newRuns(plan: readonly PlannedRun[]): PlannedRun[] {
  return plan.filter((run) => !existsSync(`${run.runDir}/result.json`));
}
```

### Pattern 2: one `plugin eval` invocation per run (D-02)

```bash
# Stage first; R is the run folder; ablation is with-without only for the arm that also yields the no-plugin baseline (D-06)
claude plugin eval "dist/eval/<ref>/lz-tdd" --case "<case>" --runs 1 --model claude-sonnet-5-5 \
  --ablation with-without --threshold 0 --trust-plugin --no-publish \
  --judge-model claude-sonnet-5-5 --output-dir "<R>" --json "<R>/plugin-eval.json"
# doing suites add: --allow-tools Write Edit     real-repo cases add: --scaffold
```
Put the target first, because `--allow-tools`, `--tag`, `--disallow-tools` and `--json` read a following target as
their own value [CITED: plugin-evals, "Choose what to evaluate"]. Spawn the real `claude.exe`, not the `claude`
shim on PATH. `~/.local/bin/claude` is a 622-byte shell shim beside `claude.cmd` and `claude.ps1` (measured), and
Node's `spawn` without a shell cannot run a `.cmd` [ASSUMED]. Take the binary path from a variable (default: the
run-slim path), which is also how the stub replaces it.

### Pattern 3: the D-03 dry run

- `stub-claude.ts` takes `plugin eval <target> --case C ... --output-dir R --json J`. It sleeps a configurable time,
  then writes `J` in the F1 shape (one case, `arms.with`/`without` with one run each, `tracePath` set to a
  `trace.jsonl` it writes with `system/init.model` = the `--model` value and a `result` line with `modelUsage`).
  Env switches make it emit a limit-stop error, a wrong model, or exit 130 without `J`.
- `stub-run-slim.ts` honours `--out` and `--resume`. It writes `{cwd, args, prompt, status, ms, stdout, stderr}` with
  `stdout` = one JSON result object (`session_id` UUID, `modelUsage`, `total_cost_usd`, `result`), and can sleep or
  emit the limit text.
- The dry run: plan 2 models x 3 cases x 2 runs per backend, kill the process tree after the first few complete
  (`taskkill /T /F`, as run-slim's watchdog does). Assert that the next `run` starts exactly the missing runs and
  refuses the died one. Then `rerun` it, and check that `resume` on a slim run passes `--resume <id>` and writes
  `result-resume-1.json`.

### Anti-patterns to avoid
- **Reading `suite.modelOverride` as the model that ran.** It echoes the flag (F1).
- **Treating exit 1 as a failed invocation.** It is also "a case below threshold"; use `--threshold 0` and read the
  JSON (F1).
- **Using `score` or `passRate` for trigger suites under `with-without`.** `tool_used: Skill` is excluded there.
  Aggregate `graders[].passed` yourself, or run trigger suites with `--ablation none` (the no-plugin arm says nothing
  about firing).
- **Granting Write/Edit to trigger cases.** `--allow-tools` is per invocation. The harness passes grants per suite,
  so read-only suites stay read-only.
- **Committing traces or `plugin-eval.json`.** They hold local paths and the account's temp folders.
- **Absolute local paths in committed scaffold scripts.** Generate them at staging time into the ignored stage
  (lz-oop committed one, `checkout.sh`, in a private repo).

## Common Pitfalls

### Pitfall 1: the trace is gone when you need the model
**What goes wrong:** the D-10 model check reads `tracePath` days later and finds nothing.
**Why:** temp cleanup (F1: `claude-eval-L4SmUL` gone).
**Avoid:** copy every `tracePath` into the run folder in the same step that ends the invocation, and refuse to
write `result.json` without it.
**Warning sign:** a run folder with `plugin-eval.json` and no `trace-*.jsonl`.

### Pitfall 2: a limit-stopped plugin-eval run reads as a scored 0
**What goes wrong:** usage-limited runs count as failures of the skill (the lz-oop Sonnet suites had 29 and 18).
**Why:** they score 0 and the suite is not `partial` (F1).
**Avoid:** when `error` matches the limit or API-error text, keep the raw files, write no `result.json`, and count
the run as not done.

### Pitfall 3: a killed slim session has no session id in `--out`
**Why:** `--output-format json` prints nothing until the end (F3).
**Avoid:** recover the id from the run cwd's transcript folder (one session per cwd); refuse `resume` when there is
none, and say to `rerun`.

### Pitfall 4: retirement breaks the kept battery
**Why:** F4 imports; F5 stale grandfather lines.
**Avoid:** the keep list above; one commit per deletion group with its grandfather lines; run both `check` scripts.

### Pitfall 5: Windows path escaping in `input_match`
**Why:** `input_match` sees `JSON.stringify(input)`, so `C:\...\references\x.md` appears as
`C:\\...\\references\\x.md`.
**Avoid:** `references[\\/]+name\.md`, as lz-oop does; cover it in a grader-model fixture with a Windows path.

### Pitfall 6: doing cases that cannot run tests on `plugin eval`
**Why:** Bash is removed from the session when it is not granted (F1), and granting it refuses the run on native
Windows. A Phase 23 skill asked to run tests says so or gives up.
**Avoid:** plugin-eval doing graders check the edit and the report line only. "Ran the tests" and "<n> tests green"
truth are slim-suite facts. Write `GREEN` regexes that do not demand a real count, or keep the count check for slim.

### Pitfall 7: concurrency and the shared rate limit
**Why:** plugin-eval runs share one rate limit (docs), and old harness notes show throttling reads as a false
non-trigger (lz-tpp `EVAL-RESULTS.md:22-31`).
**Avoid:** a default worker count of 2-4 for plugin-eval invocations, and serial for slim apply under the heavy
lock. The pilot checks whether recall drops at the chosen count.

### Pitfall 8: Write/Edit scope on native Windows
**Why:** not measured (F1). A bare `Write` grant may allow writes outside the temp workspace [ASSUMED].
**Avoid:** grant `Write`/`Edit` only to doing suites. In the pilot, add a negative case that asks for a write
outside the workspace and confirm it is denied, before the baseline.

## Code Examples

### Reading the model that ran from a plugin-eval trace (pattern, inferred from the measured trace shape)
```typescript
// Models the child really used: the init line's model and every modelUsage key of its result line.
export function traceModels(lines: readonly string[]): { init: string | null; used: string[] } {
  const entries = lines.flatMap((line): unknown[] => {
    try {
      return [JSON.parse(line)];
    } catch {
      return [];
    }
  });
  const init = entries.find((entry) => isRecord(entry) && entry['type'] === 'system' && entry['subtype'] === 'init');
  const result = entries.filter((entry) => isRecord(entry) && entry['type'] === 'result').at(-1);
  const usage = isRecord(result) ? result['modelUsage'] : undefined;

  return {
    init: isRecord(init) && typeof init['model'] === 'string' ? init['model'] : null,
    used: isRecord(usage) ? Object.keys(usage) : [],
  };
}
```
Note: the lz-red e2e record lists auxiliary `claude-haiku-4-5-20251001` usage in `modelUsage`, from calls the CLI
makes on its own [VERIFIED: `e2e-red-gilded-rose/EVAL-RESULTS.md:34-38`]. So the check is "the requested model is
the init model and is in `used`", not "`used` has one key".

### Wilson interval (for D-12)
```typescript
export function wilson(passed: number, total: number, z = 1.96): readonly [number, number] {
  if (total === 0) {
    return [0, 1];
  }

  const p = passed / total;
  const z2 = z * z;
  const centre = (p + z2 / (2 * total)) / (1 + z2 / total);
  const half = (z * Math.sqrt((p * (1 - p)) / total + z2 / (4 * total * total))) / (1 + z2 / total);

  return [Math.max(0, centre - half), Math.min(1, centre + half)];
}
```
